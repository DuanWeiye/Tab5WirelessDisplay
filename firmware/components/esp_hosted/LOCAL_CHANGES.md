# esp_hosted 本工程副本：相对官方 1.4.0 的改动

本目录是 `espressif/esp_hosted` 1.4.0 的主机侧副本（只留 `host/`、`common/` 和构建文件），
`main/idf_component.yml` 用 `override_path` 指到这里。C6 从机固件仍是官方 1.4.0，没有动。

看具体改了什么：和组件库里的 `espressif/esp_hosted` 1.4.0 逐文件对比。
文中提到的提交号和测试日志（`tools/dispbench/logs/…`）是开发时私有仓库里的，没有随这个仓库发布。

## 为什么改

官方 1.4.0 主机侧的 SDIO 收发缓冲全部用内部 DMA 内存，用量没有上限，分配失败就 `assert`：
流式接收的双缓冲按「见过的最大突发」整块重新分配、只增不减；每包缓冲和发送缓冲的内存池只增不减。
内部内存吃紧时来一次突发（大包 ping 洪泛、UDP）设备就断言重启。

上游在 2.12 / 3.1 里修了同样的问题，但升级要连 C6 从机固件一起重刷（刷坏只能靠配件救砖），
所以留在 1.4.0 按同样的思路自己改。

## 改了什么

只支持 SDIO 流式接收模式（`CONFIG_ESP_HOSTED_SDIO_OPTIMIZATION_RX_STREAMING_MODE`），别的模式编译时报错。

### 接收（`host/drivers/transport/sdio/sdio_drv.c`）

- **流式接收缓冲定长**：一块 13824 字节（1536 字节前置余量 + 12288 字节数据区），内部 DMA 内存，
  `transport_init_internal` 里分配一次，之后不变。去掉了双缓冲和 `sdio_rx_buf` 拆包任务。
- **分段读**：一次突发（从机最多攒 20 包 = 30720 字节）比数据区大时分几笔读，每笔最多 24 个 512 字节块，
  地址是「结束地址 − 这次突发还剩多少没读」（IDF 的 SDIO 从机协议允许一次读取分多笔传输）。
  读一段就在读任务里直接拆一段；段尾被切开的半个包挪到数据区前面的余量里，和下一段拼起来再拆。
- 每段读完就放开总线锁再拆包（入队在队列满时会等，不能让发送任务跟着等）。
- 流里出现坏包头：这次突发剩下的部分照读但不再拆，记一次「坏流」。
- SDIO 读数据出错：同一笔重读，最多 2 次；还读不出来就重启主机。见下面「出错后的恢复」。
  每失败一笔计一次（「SDIO 读出错」），限流告警和 `hosted` 里带最近一次的错误码。
- **每包缓冲放 PSRAM**，上限 62 块（3 个优先级队列 × 20 + 处理任务手里 1 块 + 读任务正在入队 1 块）。
  拷进包以后把包后面的部分清零（原版是整块先清零再拷，效果一样，少写一半以上）：
  下游有的处理函数（HCI、INIT 事件）不核对包长就按包内字段读。
- **交给 lwIP 的那份拷贝放 PSRAM**（`sdio_process_rx_task`）。原版用 `malloc`，小块优先落在内部 RAM；
  应用来不及读时，每条 TCP 连接会攒下一个接收窗口那么多的包，窗口 64K 时一条连接占 43KB 内部 RAM（实测）。
  上层用 `free()` 释放，对 PSRAM 的块同样适用。留在内部 RAM 的只剩 lwIP 给每个包分配的 pbuf 头（几十字节）。
- 拿不到每包缓冲、上交前的拷贝拿不到内存：丢这一包并计数，不断言。

缓冲为什么这么放：
- SDIO 读的目标缓冲必须在内部内存。本工程实测过 SDMMC 直接 DMA 到 PSRAM 会随机进入慢态。所以靠分段读把它做小，而不是挪去 PSRAM。
- 流式接收缓冲和发送的拷贝缓冲在 `transport_init_internal` 里分配。现在它由 `app_main` 开头的
  `esp_hosted_init()` 调到，内部 DMA 内存还是整块的，时机最早而且确定。
  **如果哪天又把 `esp_hosted_init()` 挪回调度器启动之前（构造函数），这两块不能留在那里**：那时内部堆只有
  最前面的 66KB 可用（其余要等主任务起来才并入堆），多占 13.8KB，紧接着创建 IDLE 任务时
  栈就落到 TCM 区，开机断言、循环重启（2026-11-11 实测踩过，当时改成了任务起来后才分配）。

### 发送

- `transport_drv.c`：`transport_drv_sta_tx` / `ap_tx` 拿不到发送缓冲时返回 `ESP_ERR_NO_MEM`（lwIP 当作这一包没发出去，
  TCP 自己重传），限流告警；通道发送池上限 `H_SDIO_TX_Q + 4` 块，用完只留 4 块备用。
- `sdio_drv.c`：非零拷贝发送（串口命令即 RPC、蓝牙 HCI）不再用池子，改成一块常驻的拷贝缓冲 `tx_copy_buf`
  （1536 字节，内部 DMA）。只有写任务用，一次只发一包；`transport_init_internal` 里分配一次，每包用前清零。
- 上游原有的两处「直接重启主机」（从机不响应、发送重试后仍然失败）改走 `sdio_recover_by_restart`，
  和接收侧共用连着重启的次数上限。从机不响应那一处在没有重启时返回「没有缓冲」，这一包丢掉。
- 发送缓冲要直接交给 SDIO，仍然是内部 DMA 内存。

### TCP 纯 ACK 合并（`tcp_ack_hold.{h,c}`、`tcp_ack_hold_core.c`、`transport_drv.c`、`sdio_drv.c`，2026-11-14）

**现象和根因。** 无线显示投屏（15~20 Mbps 下行）时，发送端每几秒就有一帧的确认迟到 150~300 ms。查下来是上行丢包：
Tab5 发给电脑的包约 1% 没到，丢到带数据的小段（每帧的应用层确认、触摸和键盘事件）时要等 TCP 超时重传（160~260 ms），
这期间这条连接上 Tab5 发出的东西全被压住；发送端在途帧数到上限后也发不了新帧。
（对画面的影响比当初以为的小：发送端在确认迟到时会多放两帧在途，画面大多接着走，见下面的实测。受影响更直接的是回传的触摸 / 键盘事件。）
包都交到了 C6（主机侧三处可能丢包的地方计数全是 0）；空闲时 ping 不丢，只在大量收数据时丢。
原因是 lwIP 每收两个段回一个纯 ACK，每秒一千多个，而且是一阵一阵的（SDIO 一次突发交上来十几二十个段，协议栈连着回十来个）。
官方 1.4.0 从机固件往 WiFi 发不出去时（`esp_wifi_internal_tx` 失败）最多重试 6 次、前后几毫秒，然后**悄悄丢掉**：
不排队、不通知主机；限流（`wifi_tx_throttling`）看的是 SDIO 到 WiFi 之间那个队列的占用，WiFi 发送缓冲满了它不一定触发（实测 0 次）。
新版从机（到 3.1.0）只是多重试几次，重试用尽照样丢。所以在主机侧少发：纯 ACK 是累计确认，后一个包含前一个的全部信息。

**做法。** `transport_drv_sta_tx`（lwIP 往 STA 发包的入口）先问 `tcp_ack_hold_on_tx`：
- **可以合并的纯 ACK**（IPv4、不是分片、TCP、没有载荷、IP 头和 TCP 头都没有选项、标志位只有 ACK）先暂存在这条连接的槽里，
  同一条连接后来的盖掉前面的；从第一个暂存起最多等 `ACK_HOLD_DEFAULT_US`（2 ms），单次 `esp_timer` 到点把暂存的发掉。
- **原样、立刻发的**：带数据的段（不延迟）、带选项的确认（丢包时的重复确认带 SACK 块）、SYN / FIN / RST、
  以及**重复确认**（和这条连接上一个带确认的包确认号、窗口都一样的纯 ACK——对端数到 3 个才快速重传，个数不能变）。
  IPv6 的不看，照常发（本工程的设备没有 IPv6 地址）。
- 同一条连接随后发了别的包，暂存的那个怎么办：新包的确认号更新，或者确认号一样而新包带数据 / FIN → 暂存的作废
  （协议栈每次发包都填当前的确认号和窗口）；新包没有载荷、确认号和暂存的一样（重复确认，带不带 SACK 块都算）→ **暂存的先发**，
  对端先看到确认号推进，后面的才从第 1 个重复确认数起。
- 表里记 8 条连接（本机发过 TCP 包的都记，记的是最近的确认号和窗口），不够时让出最久没动的；
  让出来的槽里还暂存着东西就先发掉。
- 到点时在 esp_timer 任务里发，不能等：`sdio_drv.c` 加了不等待的入队 `esp_hosted_tx_nowait`。
  发送队列满、拿不到发送缓冲、从机叫停时不丢，留在槽里下一轮再发；链路不通才丢。
  发送缓冲已经全在途时不去要（不然每 2 ms 给内存池的「分配失败」加一，那个数是留给真丢包看的）。
- 表用互斥锁保护，到点时**拿着锁取出并入队**：放了锁再发的话，协议栈线程可能正好在空当里发了同一条连接的下一个包，
  旧的纯 ACK 排到它后面，对端会多数一个重复确认。（这是开发时的第一版——自旋锁、取出来放了锁再发、发不出去再放回——
  被当时的随机序列测试测出来的；现在的做法里没有这个空当，现在的单元测试也就模拟不了它。）协议栈线程在锁里只做判定，它自己那一帧在锁外发。
- 判定逻辑（`tcp_ack_hold_core.c`）不依赖 FreeRTOS，单元测试 `firmware/tools/ackholdtest/run.sh` 在电脑上跑：
  照真实情况拼的帧 + 随机序列对照模型（不可合并的包一个不少、先后不变；每条连接最后到对端的是最新的确认号和窗口；
  重复确认的个数不多不少；同一次连接里对端看到的确认号不往回走）。
- `hosted` 多打一行合并统计；`hosted ackhold <微秒>` 临时改暂存时间（0 = 不合并，不落盘），新旧对比用。
- 「发送限流：从机叫停 N 次，叫停期间被拒的包 M 个」「等过从机腾接收缓冲 / 丢掉」是定位时加的计数，留作正式的。

**没选的办法。** 升级从机固件：治不了根（还是丢），还要重刷 C6。把确认 / 输入挪到 UDP：和「触摸、键盘回传与画面同一条连接」的约定冲突，
而且别的 TCP 下载同样受益不到。调 lwIP 的重传定时器：只是让每次停得短一点。

### 初始化（`host/esp_hosted_host_init.c`、`main/app_main.cpp`）

- 去掉了原版的构造函数。原版靠它在调度器启动之前调 `esp_hosted_init()`，那时内部堆只有最前面的 66KB 可用，
  esp-hosted 一个组件用掉 27KB，到创建 IDLE 任务时余量不到 17KB。
- 现在由 `app_main` 开头显式调用 `esp_hosted_init()`，排在最前面：和原来一样早于其它初始化，
  并且趁内部 DMA 内存还是整块的时候把定长收发缓冲拿到手。这一步只建队列 / 任务、初始化 SDMMC 主控，
  不碰 C6 本身：C6 的电源由 `board::init` 经 IO 扩展芯片打开，复位和 SDIO 卡初始化要到 `esp_wifi_init` 才做。
  TF 卡用到时才挂载，和 C6 共用 SDMMC 主控（IDF 5.4.2 的 `sdmmc_host_init` 对已初始化的主控直接返回成功）。
  进入 `app_main` 时最前面那块堆还剩 42KB。
- 没调就用 WiFi：`esp_wifi_init()` 报 `Transport not initialized, call esp_hosted_init() first`、返回失败，wifi 任务结束（不中止）。
- 往 `app_main` 里再加初始化时看主任务栈：开机日志 `ui ready（主任务栈最低余量 …）`，现在 1540 字节（共 3584）。

### 出错后的恢复（`transport_drv.c`、`sdio_drv.c`，2026-11-12）

从机（IDF `sdio_slave` 的流模式）是一批一批发的：把排着队的包全部取出来当作在途的一批、更新长度寄存器、
发新包中断，**要等主机把这一批读完才取下一批**。所以主机读数据出错后如果放下这次突发去等下一次中断
（上游就是这么做的），从机会一直停在这一批上，再也没有新包中断：WiFi 收不到任何包、RPC 全部超时，
而且日志里没有后续迹象。实测（注入「跳过一笔读取」）确认如此。

SDIO 驱动（`sdio_drv.c`）里的处理：
- **读数据出错 → 同一笔重读**（最多 2 次）。地址是「结束地址 − 还剩多少没读」，从机没把这一笔发出来的话，
  重读拿到的就是它，一个字节都不丢。重读后仍然出错 → 重启主机。
- **读寄存器（中断状态、可读长度）出错 → 重读**（最多 2 次，读这几个寄存器没有副作用），还不行 → 重启主机。
  上游读不出来就放下、等下一次中断，后果和上面一样。
- 读得出来、但**连续 8 次突发都拆不出包**（流错位，对不回来）→ 重启主机。偶发的单个坏包只坏一次突发，不会连续。
- **SDIO 卡初始化失败** → 重启主机。上游在这里从任务函数返回，FreeRTOS 里等于 abort。
- 发送侧上游原有的两处重启（从机不响应、写数据重试后仍失败）也走同一个出口。
- 以上都经 `sdio_recover_by_restart`（打一行 SDIO 统计）调传输层的 `transport_recover_by_restart`。

传输层（`transport_drv.c`）里的处理：
- **从机复位后一直没有就绪**（`transport_drv_reconfigure`）：等 10 秒（正常约 1.3 秒）还没收到 INIT 事件就重启主机。
  上游每 10 秒再复位一次从机、一共等 1000 秒，然后返回失败，而调用方全是 `ESP_ERROR_CHECK`：从机起不来时设备卡 17 分钟后 abort。
  而且 SDIO 下从机被再次复位以后要主机重新枚举才能通，枚举只在读任务启动时做一次，所以头 10 秒没起来、后面怎么等都起不来；
  重启主机才会重新枚举。调用方（`esp_hosted_api.c` 的 `esp_hosted_reconfigure` / `esp_hosted_reinit` / `esp_wifi_remote_init`，
  `vhci_drv.c` 的两处）改成返回错误或打日志，不再 abort。
- `transport_recover_by_restart`：**连着重启有上限**。重启前把「这是连着的第几次」写进 RTC 内存，下一次开机在 `transport_drv_init` 里取出来。
  只有复位原因是软件重启、而且这句话是上一次开机留的，才接着数；所以手动复位、断电、panic，
  以及中间夹着的别的软件重启之后都从 0 数起。为恢复链路重启出来的这次开机不到 10 分钟就又要重启的算连着的，
  跑满 10 分钟才出事的从 0 数起。连着 3 次还没好就**判定链路故障**，不再重启。`hosted` 最后一行打印当前状态。
  为恢复调的 `esp_restart` 如果卡在关机处理里被看门狗复位，复位原因不是软件重启，这一次不计数。
- **判定故障之后**（`transport_failed`，到下次开机为止不会清）：
  - `esp_hosted_tx` 立刻返回失败，不排队、不逐包打日志；写任务把队列里剩下的包直接丢掉（握手还没完成的话直接停住）；读任务停住。
    三个任务都不再碰总线（SDMMC 主控和 TF 卡共用）。`transport_drv_reconfigure` 立刻返回失败，不再复位从机。
  - RPC 请求因此马上得到「发送失败」的应答（约 20 ms，主要是打日志），`esp_wifi_*` 返回错误，不用各等 5 秒超时。
    这条路在上游是坏的，见下面「RPC」。
  - 应用查询（`host/api/include/esp_hosted_bufstat.h`，都只读标志）：`esp_hosted_link_failed()` = 已经判定故障；
    `esp_hosted_link_up()` = 握手完成而且没有故障（要用蓝牙 HCI 之前拿它把关）。
    本工程里：`wifi::status()` 据此报 `State::Fault`，wifi 任务把网络接口放下来、不再编排连接（开机阶段就故障的话
    `esp_wifi_init` 返回失败，wifi 任务结束）；状态栏显示红色警告图标、不显示 KVM 图标，设置页 WiFi 行显示「故障」，
    WiFi 页显示「无线模块故障，请重启设备」，KVM 页写「无线模块故障」；点设置页的「故障」或 WiFi 页的故障文字弹「重启设备？」确认框。
    `ble_hid::start()` 在链路没起来或故障时不起蓝牙栈；蓝牙栈已经在跑的话，kvm 任务里的 `ble_hid::housekeeping()` 把它停掉
    （`nimble_port_stop()`；不停的话 NimBLE 每 100 ms 重试一次控制器复位并打日志，一直到关机）。
- 以后如果打开 `CONFIG_ESP_HOSTED_SDIO_CHECKSUM`：校验失败也算坏突发，连续 8 次就重启，到时要重新评估这个阈值。

主机分不出「从机没发出来」和「从机发了、主机没收到」。后一种情况下重读会读过头，实测有两种结果：
从机当时没有别的包在途 → 之后的命令全部超时，走到重启；从机已有下一批在途 → 错位一两次突发后自己恢复。
选「重读」是因为不重读的话前一种情况会永久停住；后一种情况最坏是一次自动重启。

验证要用带故障注入的临时构建。注入补丁和分步测试脚本在 `tools/dispbench/rxfault_testbuild/`：
`git apply -p0 firmware/tools/dispbench/rxfault_testbuild/inject.patch` 套上（在仓库根目录），测完 `-R` 撤掉
（改了 `sdio_drv.c` / `rpc_core.c` / `debug_console.cpp` 里它碰的地方以后要重新生成：`git apply --check -p0 …` 核对），
**带注入的代码不提交**（代码里都标了 `TESTBUILD`）。它加的调试台命令：
- `hosted fault <n>`（接收侧）：1 = 跳过下一笔读取并当作出错；3 = 一直如此；2 = 下一笔照读、读完当作出错；
  4 = 同 2 但只挑分段突发的非末段；5 = 把每次突发的第一个包头清零；6 = 只清一次；
  7 = 读寄存器一直当作出错；8 = 只错一次；9 = 读任务在下一次中断后先睡 8 秒（让在途的 RPC 应答迟到）。
- `hosted txfault <n>`（发送侧）：1 = 查从机发送缓冲数一直报「从机不响应」；2 = 写数据一直当作失败。
- `hosted bootfault <n>`（开机阶段，标志放 RTC 内存，软件重启后还在，别的复位之后作废；0 = 撤掉）：
  1 = SDIO 卡初始化失败；2 = 数据一直读不出来（从 INIT 事件那次突发起）；3 = INIT 事件收到就丢（从机一直不就绪）；
  4 = 寄存器一直读不出来。
- `hosted semfail <n>`：接下来 n 个同步 RPC 的信号量当作建不出来（内部内存用光）。
- `hosted swreset`：和链路无关的软件重启。
- `hosted uitest`：拿着 LVGL 锁、照界面的方式调 `wifi::set_enabled` / `scan_start` / `connect_saved`，打印每一步耗时。
- `hosted rpcfail <n>`：连发 n 个 RPC，打印失败数、耗时、前后堆空闲和堆完整性。
- `hosted uifind`：遍历当前屏幕和顶层的对象树，打印故障相关的 label（「故障」、故障文字、确认框按钮、状态栏图标）的坐标、
  是否可见、文字颜色、可不可点；`hosted uiclick <文字>`：点一下文字以它开头的 label（它自己不可点就点父对象）。

`rxfault_seq.sh <日志> <设备IP> <步骤>...` 逐步注入，自动等重启 / 重新联网；判定故障后自动跑上面几条和各个页面，
再静置（`QUIET` 秒）数日志行数、看有没有重启；每一步都检查日志里有没有崩溃痕迹。步骤写法见脚本开头。

### RPC（`rpc_core.c`、`serial_if.c`、`serial_drv.c`、`serial_ll_if.c`，2026-11-12）

**发送失败的出口。** RPC 请求发不出去时（`esp_hosted_tx` 返回失败：传输层没就绪，或者链路已经判定故障），上游的本意是给同步调用方
一个失败应答、马上叫醒它。这条路在 1.4.0 里有三个问题，判定故障以后它成了常走的路，所以一起修了：
- **发送缓冲重复释放**：`esp_hosted_tx` 失败时已经释放了缓冲，`transport_pserial_send` 又释放一次，堆断言重启
  （本工程早先「传输层没起来就发 RPC，`tlsf_free` 断言」踩的就是它）。现在缓冲交给 `serial_drv_write` 以后归下层，
  成败都由下层释放；`serial_drv_write` 和 `serial_ll_write` 里没交到 `esp_hosted_tx` 就失败的几处补上释放。
- **失败应答没带请求的 uid**：按 uid 找不到等待者，调用方叫不醒，照样等满 5 秒；失败应答留在应答队列里没人取，
  攒满（3 个）以后 RPC 发送任务卡在入队上，之后所有 RPC 都发不出去。现在带上 uid。
- **请求交出去之后还在用它**：同步调用方一被叫醒就释放请求（可能在另一个核上），发送任务随后还读它、
  按里面的指针释放内存；成功路径上也一样（请求发出去以后应答随时会到）。现在请求带的缓冲在发送之前释放，
  发送之后只用开头记下来的局部变量（uid、消息号、回调）。

**同步应答的交付。** 上游把应答放进一个公用的队列（`rpc_rx_q`）再叫醒调用方，调用方取队头、不核对 uid：
- 调用方超时以后才到的应答照样进队列，之后每个请求取到的都是上一个请求的应答，一直错位到重启；
- 两个任务同时发同步请求时，可能互相取到对方的应答；
- 请求号（uid）的自增没有保护，两个任务同时发请求可能取到同一个号。

现在应答按 uid 直接放进等待者登记的表项（`deliver_sync_resp`），等待者从自己的表项里取；登记、交付、取走并注销都在一把锁
（`sync_rsp_lock`）里做，取号也在锁里。没人等的应答（调用方已超时）丢弃并打一行告警，连带它的附属缓冲一起释放；
刚超时、应答正好到的情况下，应答已经在表项里，照常使用。`rpc_rx_q` 删掉了。
验证：注入 9（读任务睡 8 秒）期间查 C6 版本，5 秒超时；读任务醒来后迟到的应答被丢弃；之后再查版本、读 MAC 都正确。

**登记不上就不发。** 同步请求的信号量建不出来（内部内存用光）时，这次请求直接按失败返回、不登记表项。
登记一个空信号量的话，等待方看到空就返回、不注销，这个表项和之后到的应答都收不回来；表只有 5 项，
占满以后所有同步 RPC 都报 `out of buffer space`，要重启才好。`RPC_SEND_REQ` 宏在 `rpc_send_req` 失败后不再读已经释放的请求。

没处理的（上游原有）：
- 异步请求（带回调的）那一半没动，本工程没有用到，也没有验证过。
- 同步请求超时以后调用方释放请求，如果这时请求还排在发送队列里没轮到（发送任务被堵了 5 秒以上），发送任务之后会读到已释放的请求。
  平时发送任务不会堵这么久；链路判定故障后所有发送立刻失败，也堵不住。
- `rpc_send_req` 把请求排进发送队列失败时不注销刚登记的表项（信号量却销毁了）。入队是无限等，队列存在就不会失败，走不到。
- `rpc_send_req` 入队之后还释放一次请求带的缓冲（`app_free_buff_*`），和发送任务里的释放重复。现在没有请求设置这个字段，走不到；
  以后有请求要带缓冲时，先把 `rpc_send_req` 里那一处删掉（缓冲归发送任务）。

### 内存池（`host/drivers/mempool/mempool.{h,c}`）

- 新增 `mempool_create_ex(block_size, heap_caps, max_blocks, max_cached)`：可以指定内存类型
  （0 = 内部 DMA 内存）、块数上限（到上限 `mempool_alloc` 返回 NULL）、空闲块保留上限（多出来的还给堆）。
  原 `mempool_create` 行为不变（不限、全留）。
- 新增 `mempool_get_stats`。
- 内部 DMA 内存的块改用 `heap_caps_aligned_alloc` 分配（条件和 `MEM_ALLOC` 相同：`MALLOC_CAP_DMA`、
  64 字节对齐、长度是 64 的整数倍），不再经 `esp_dma_capable_malloc`：它每失败一次打一行错误日志，
  内存吃紧时实测几千行，会拖慢正在收发包的任务。

### 其它

- `host/drivers/rpc/core/rpc_rsp.c`：WiFi 扫描结果和已连接站点列表的条数按实际带来的记录数截断

## 怎么看、怎么测

- 调试台 `hosted`：打印上面那组统计。正常情况下「坏流」和「SDIO 读出错」必须是 0，「连着重启过」是 0。
- 出错后的恢复和判定故障：`tools/dispbench/rxfault_testbuild/`（故障注入，见上面「出错后的恢复」）。
- 调试台 `netrx tcp <IP> <端口> [秒] [每秒最多读多少KB]` / `netrx udp <端口> [秒]`：收包自测，配套发送端 `tools/dispbench/nettx.py`。
  带第 4 个参数时限速读，让接收窗口填满；每秒那行打印内部内存空闲，用来看积压的包占不占内部 RAM。
- 调试台 `?` 发起 WiFi 扫描，`w` 打印状态和上一次扫描的结果。
- 调试台 `disp dmahog on|off`：占满 / 释放内部 DMA 内存，复现内存吃紧。
- `tools/dispbench/netstress.sh`：大包 ping 分级洪泛。
- `tools/dispbench/udpstress.sh`：UDP 分级灌包，每级后打印统计。
- `tools/dispbench/nomemtrial.sh`：占满内部 DMA 内存后六路并发 ping 洪泛 + UDP，再释放看恢复。
- `tools/dispbench/nettrial.sh`：每轮硬复位后静置 90 秒再分级 ping 洪泛（当初复现断言的流程）。

分段读在 UDP 下很少触发（主机读得快，30 Mbps 下一次突发最多 10178 字节）；TCP 64K 窗口全速收包时会触发
（12 秒约 80 次，最大突发 2 万字节上下）。改了分段读或拆包逻辑后，要用两个临时构建专门验证（不提交）：
1. 把 `RX_STREAM_CHUNK_MAX` 改成 `4 * ESP_BLOCK_SIZE`，跑 `udpstress.sh` 多种包长，每个包都会跨段；
2. 保持真实段长，在读任务的 `for (;;)` 开头每 64 次循环 `vTaskDelay(20ms)` 一次，让从机攒满 20 包。

## 审查里提了、没采纳的

- 通道发送池只留 4 块备用（`H_SDIO_TX_Q + 4` 上限不变）：实测正常流量在途最多 2~4 块，够用。
- `MEMPOOL_ALIGNED` 对已对齐的长度多加 64（每块多占 128 字节）：上游原有。改它等于改所有池的块大小，
  收益约 0.5KB，不值得为它把上面的测试重跑一遍。
- ~~`CONFIG_LWIP_TCP_OOSEQ_MAX_PBUFS=4`（第二轮审查的存疑）~~：2026-11-13 实测确实如此（丢一个段之后帧率掉到 1~2 帧/秒、最后超时断开），已改成 12 并开了 SACK，见上面「其它」里 TCP 接收窗口那一条。
- RPC 字符串字段（`ssid[33]` 等）在从机发来满长度数据时没有结尾 NUL（第二轮审查的存疑）：只在从机行为异常时出现，
  读不出所在的结构体。没改。
- 判定故障时停蓝牙栈，`nimble_port_stop()` 返回非 0 就不再试（二审的存疑）：只有主机任务还没跑到 `ble_hs_start` 的那几毫秒里判定故障才会碰到
  （那时停不掉，之后主机任务会每 100 ms 重试并打日志，到重启为止；不影响别的功能，界面上照常提示重启）。
  要测得人为把故障卡在这几毫秒里，没有做；没测过的重试逻辑不加。
- 判定故障时有蓝牙主机连着（二审的存疑）：`nimble_port_stop()` 要等断开事件，内部约 2 秒超时，kvm 任务会被堵几秒。有界，没有实测。

## 以后升级上游

`espressif/esp-hosted-mcu` 3.1 起自带定长接收缓冲、内存池可放 PSRAM、分配失败不断言。
哪天决定连 C6 从机固件一起升级，就整体换成上游版本、删掉这个副本和 `override_path`，这里的改动不用往上搬——

（换完先用 `hosted ackhold 0` 对比一下还需不需要）。
