# Tab5 无线显示协议（v2）

> v2 = v1 加上认证、加密和自动发现（取舍见 `AUTH_DESIGN.md`）；画面、输入、流量控制这些和 v1 一样。**没有明文模式**，v1 的发送端连不上 v2 的 Tab5。
> **实现进度**：固件、Python 工具（`tools/`）、C# 发送端的核心 + 命令行程序（`sender/`，含自动发现和自动连接）都已经是 v2，对真机回归过；C# 这边往 Windows 里注入触摸和按键也有了（`wdsend --input`），托盘程序（`sender/src/WinDisplay.Tray`，常驻、自动连接）有了第一版。

## 角色

- **Tab5 = 服务端**，监听 TCP 端口 `7250`，同一时刻只服务一个发送端。
- **发送端**（下面也叫「电脑」；第一个实现：Windows + C#，`windisplay/`）主动连上来，发画面，收触摸和键盘。
- 画面下行、输入上行走**同一条 TCP 连接**。
- 两边先**配对**一次（在 Tab5 上输一遍电脑那边设的密码），之后每次连接用配对留下的密钥互相认证，握手之后的报文全部加密（见「认证和加密」）。
- 发送端不用填 Tab5 的地址：在局域网里广播询问，等着连接的 Tab5 会应答（见「自动发现」）。

## 画面的几何关系（发送端必须照做，Tab5 不旋转、不缩放）

Tab5 的面板原生是竖屏 **720 × 1280**，帧缓冲按这个方向排列；人拿着看的是横屏 **1280 × 720**。
发送端把 1280 × 720 的横屏画面**逆时针旋转 90°** 后再编码，得到的 720 × 1280 图像就是帧缓冲的排列：

```
帧缓冲第 r 行、第 c 列  =  横屏画面第 c 行、第 (1279 − r) 列        (r: 0..1279, c: 0..719)
```

即帧缓冲的第 0 行是横屏画面最右边那一列（从上到下）。

画面按**条带**发送。一个条带是帧缓冲里的若干整行（宽固定 720，高是 16 的倍数，起始行是 16 的倍数），
对应横屏画面里的一个竖条。每个条带是一张独立的 JPEG：

- 基线（baseline）JPEG，不能是渐进式；YCbCr 三分量；色度采样看这条连接走哪种帧缓冲（见下面「画面的色彩」）：
  走 YUV422 的只能是 4:2:2，走 RGB565 的 4:2:0 / 4:2:2 / 4:4:4 均可；
- 宽必须是 720，高必须是 16 的倍数，`起始行 + 高 ≤ 1280`；
- Tab5 用硬件解码器把它直接解到帧缓冲对应的行里。

**条带的 JPEG 文件头要规整。** Tab5 在把条带交给硬件解码器之前会把文件头严格检查一遍，不合格就断开连接
（解码器的驱动自己不查边界，坏数据会写坏内存，所以这一关不能省）。要求：

- 以 SOI（`FF D8`）开头，后面是一段一段**紧挨着**的段，最后是 SOS 和压缩数据；段与段之间不能有填充字节；
- 文件头里只能出现这些段：APPn（`FF E0`~`FF EF`）、COM（`FF FE`）、DQT（`FF DB`）、DHT（`FF C4`）、SOF0（`FF C0`）、DRI（`FF DD`）、SOS（`FF DA`）；
- 量化表：表号不重复，而且正好是 0、1、…（常见的是 0 号给亮度、1 号给色度；只定义 1 号表、或者同一个表号定义两次都不行，
  解码器的驱动按「第几张」而不是按表号用表）；每个分量用到的表都要定义过；
- 霍夫曼表：DC / AC 各最多两张（表号 0、1）；每个 DHT 段里至少有一张表；SOS 里各分量用到的表都要定义过，请自带霍夫曼表
  （一张都不带时真机的解码器会用标准表，但模拟接收端解不了这样的条带）；
- SOF0：8 位精度，三个分量（灰度图不行），三个分量的编号互不相同；亮度分量的采样系数是 1×1、2×1 或 2×2，两个色度分量是 1×1；
- SOS：三个分量，编号和顺序都和 SOF0 里的一致，基线的固定参数（Ss = 0，Se = 63，Ah = Al = 0）。

libjpeg / libjpeg-turbo（PIL 用的就是它）编出来的基线 JPEG 符合，自测覆盖了 PIL 的 144 种参数组合。
别的编码器（比如 Windows 自带的）还没验过，用之前对着 `wd_mock_tab5.py` 发一帧，或者拿 `tools/wdproto.py` 的 `jpeg_size()`（同一套检查的 Python 版）验一下。

## 画面的色彩

Tab5 的帧缓冲每像素 2 字节，有两种用法，一条连接用哪一种在握手里定（见「握手」的 `caps`）：

- **YUV422**（新的发送端用它：`tools/` 下的 Python 工具、加了这一节之后的 Windows 发送端）：解码器把 JPEG 里的 Y / Cb / Cr 原样写进帧缓冲，面板的接口芯片（DSI 桥）转成 24 位 RGB 送给面板。
  亮度是完整的 8 位，平滑的灰色、渐变上没有色阶断层。对发送端有两条要求：
  1. **条带一律 4:2:2**（亮度分量的采样系数 2×1）。别的采样解码器写不成这种排列，Tab5 收到就断开。
  2. **画面先压到有限范围再编码**：三个通道各自 `v' = 16 + v × 219 / 255`（四舍五入），然后照常按 JFIF 的全范围 YCbCr 编码。
     原因：桥是按有限范围（BT.601，亮度 16 = 黑、235 = 白）把 YCbCr 换回 RGB 的，而且没有开关可以改；不压的话 16 以下全是黑、235 以上全是白，
     暗部和亮部的层次就没了。压了之后桥展开回来就是原来的颜色。（色度按标准应该缩到 224 / 255，这样做是缩到 219 / 255，
     饱和度低约 2%，看不出来；好处是三个通道过同一张表。）
- **RGB565**（加 YUV422 之前的发送端）：解码器直接解成 RGB565，全范围，色度采样 4:2:0 / 4:2:2 / 4:4:4 都收。红蓝只有 32 级、绿 64 级，
  平滑的灰色上看得出一格一格的断层，JPEG 质量再高也一样。

怎么定：Tab5 在 HELLO 的 `caps` 里置 bit1 = 「我能走 YUV422」；发送端看到这一位、自己也会按上面两条发，就在 AUTH 的 `caps` 里置 bit3，
这条连接就走 YUV422，否则走 RGB565。HELLO 里没有这一位的 Tab5 对它不能置 AUTH 的 bit3
（置了它也是按 RGB565 解，压过范围的画面会发灰）：加这一位之前的固件不认得它；新固件接管屏幕时连着 3 次切不到 YUV422，
到重启为止也不再置这一位，发送端照规矩退回 RGB565。一条连接中途不能换。

走 YUV422 的连接接管屏幕、归还屏幕时，Tab5 要把桥在两种格式之间切一次，屏幕黑两三帧（几十毫秒）。

## 报文格式

所有整数小端。每个报文 = 8 字节头 + 载荷：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `type` | 报文类型，见下表 |
| 1 | 1 | `flags` | 保留，填 0；收到不是 0 的就断开 |
| 2 | 2 | `arg` | 随类型而定的小参数 |
| 4 | 4 | `len` | 载荷字节数（加密的报文里是明文载荷的字节数，不含认证码） |

握手报文（下面第一张表，READY 除外）是明文。**AUTH_OK 之后**的报文都加密，线上是 **8 字节头（明文）+ `len` 字节密文 + 16 字节认证码**，
哪一刻开始、怎么算见「报文加密」；下面各表里写的载荷是解密之后的内容，各处的长度上限（`max_strip_bytes` 等）说的也都是明文载荷的字节数。

### 握手（明文，READY 除外）

| type | 名称 | 方向 | arg | 载荷 |
|---|---|---|---|---|
| `0x01` | HELLO | Tab5 → 电脑 | 协议版本（2） | 68 字节：`u16 fb_w`(720)、`u16 fb_h`(1280)、`u16 view_w`(1280)、`u16 view_h`(720)、`u32 max_strip_bytes`、`u32 max_frame_bytes`、`u32 caps`（能力位，见下）、16 字节 Tab5 编号、32 字节 Tab5 的名字 |
| `0x02` | AUTH | 电脑 → Tab5 | 0 | 92 字节：`u32 caps`、16 字节电脑编号、8 字节配对密钥的标识（见「每次连接」）、32 字节一次性 X25519 公钥、32 字节电脑的名字 |
| `0x03` | AUTH_OK | Tab5 → 电脑 | 0 | 32 字节：Tab5 的一次性 X25519 公钥 |
| `0x04` | AUTH_UNKNOWN | Tab5 → 电脑 | 0 | 无。「我这里没有这台电脑的这把配对密钥」（没配对过，或者两边存的不一样），要重新配对 |
| `0x05` | READY | 双向 | 0 | 无。**加密**：每个方向加密后的第一个报文，对方靠它确认这边真有会话密钥 |
| `0x06` | PAIR | 电脑 → Tab5 | 0 | 113 字节：16 字节电脑编号、32 字节电脑的名字、65 字节 `pA` |
| `0x07` | PAIR_REPLY | Tab5 → 电脑 | 0 | 97 字节：65 字节 `pB`、32 字节 `cB` |
| `0x08` | PAIR_OK | 电脑 → Tab5 | 0 | 32 字节：`cA` |

- **编号**：16 字节随机数，各自第一次用到时生成、一直留着，对方按它查配对。
- **名字**：给人看的（配对列表里显示），UTF-8，最多 32 字节，不足的补 0。电脑填机器名，Tab5 填 `Tab5-` 加几位区分用的字符。
  收到的一方只把它当显示用的文字：到第一个 0 为止；不是合法 UTF-8 的字节、控制字符（U+0000~U+001F、U+007F~U+009F）、
  看不见又能搅乱显示的字符（U+200B~U+200F、U+2028~U+202E、U+2060~U+206F、U+FEFF：零宽、换行 / 分段、方向控制）、
  「替换字符」U+FFFD 本身都换成 `?`
  （一段不合法的字节换成几个 `?` 不要求各处一致）。算摘要用的是线上的原始字节，不受这一步影响。
- **`caps`**：能力位，不认识的位忽略。HELLO 的 bit0 = **Tab5 能收声音**（见「声音」）：置了位电脑才可以发 AUDIO，
  没置位的 Tab5（加声音之前的固件）收到 AUDIO 会当成不认识的报文断开。
  HELLO 的 bit1 = **Tab5 能走 YUV422 帧缓冲**，AUTH 的 bit3 = **这条连接的条带都是 4:2:2、有限范围，走 YUV422**（见「画面的色彩」）：
  HELLO 里置了 bit1，电脑才可以置 AUTH 的 bit3；电脑没置的连接照旧走 RGB565。
  AUTH 的 bit0 = **电脑认得 INPUT_MODE**（见「触摸方式」）：置了位 Tab5 才发它，没置位的发送端（加这个报文之前的版本）收不到、照旧只有触摸一种方式。
  AUTH 的 bit1 = **电脑认得 TPAD_GAIN**（同一节）：一样的规矩，没置位的发送端按它自己的倍数加速。
  AUTH 的 bit2 = **电脑认得 PICTURE**、bit4 = **电脑认得 PICTURE_MODE**（见「画质」）：置了 bit4，Tab5 发 PICTURE_MODE（人选的是第几档）；
  只置了 bit2（加档位之前的发送端），Tab5 把档位折成一组质量和预算发 PICTURE；两位都没置的发送端按它自己的画质压。
  能力位是用来加报文、加新做法的：一方认不认得某种报文、用不用某种做法在握手里说清楚，对方照着来，
  所以加了 INPUT_MODE、TPAD_GAIN、PICTURE、PICTURE_MODE、AUDIO、YUV422 版本号还是 2。

### 发送端 → Tab5

| type | 名称 | arg | 载荷 |
|---|---|---|---|
| `0x10` | STRIP | 起始行 | 一张 JPEG（见上）。单个条带不超过 `HELLO.max_strip_bytes` |
| `0x11` | PRESENT | 0 | `u32 seq`（帧序号，发送端自增）、`u32 t_ms`（发送端时钟，原样带回，用来量延迟） |
| `0x30` | KBD_LEDS | 灯状态（bit0 Num，bit1 Caps，bit2 Scroll） | 无。主机的键盘指示灯状态，Tab5 亮在键盘模块的灯上（见「键盘」） |
| `0x3F` | BYE | 0 | 无。发送端主动结束 |
| `0x40` | AUDIO | 0 | 一段声音：48 kHz、双声道、16 位小端 PCM，左右交替；长度是 4 的倍数，4~3840 字节（最多 20 ms）。见「声音」。HELLO 的 `caps` bit0 没置位时不得发 |
| `0x41`~`0x4F` | （留给声音） | | 还没定义 |

一帧 = 若干个 STRIP + 一个 PRESENT。没变化的条带不用发。Tab5 收到 PRESENT 后在面板的帧边界把这一帧换上屏幕，然后回 ACK。
等帧边界的那几毫秒到十几毫秒里 Tab5 接着收下一帧（见「Tab5 怎么处理三块帧缓冲」），发送端不用等 ACK 就可以发（见「流量控制」）。

### Tab5 → 发送端

| type | 名称 | arg | 载荷 |
|---|---|---|---|
| `0x12` | ACK | 0 | `u32 seq`、`u32 t_ms`（PRESENT 里带来的原值）、`u32 recv_us`（这一帧从第一个条带到 PRESENT 的接收用时）、`u32 decode_us`（解码用时合计，含为追平另外两块帧缓冲补解的）、`u32 present_us`（收到 PRESENT 到换上屏幕；第一帧在这期间才解码，所以第一帧的这个数包含解码） |
| `0x20` | TOUCH | 触点数 n（0..5） | n × { `u8 id`、`u16 x`、`u16 y` }。坐标是横屏画面里的像素（x: 0..1279，y: 0..719）。每次是当前所有触点的快照：某个 id 不在里面了就是抬起，n = 0 表示全部抬起 |
| `0x21` | KEY | 0 | 8 字节 USB HID Boot 键盘报文（修饰键位图、保留字节、最多 6 个键码）。来自 Tab5 的键盘模块（见「键盘」） |
| `0x22` | MOUSE | 0 | `i16 dx`、`i16 dy`、`i8 wheel`、`u8 buttons`（bit0 左，bit1 右，bit2 中）。相对位移。预留：Tab5 现在不发 |
| `0x23` | HELD | 0 | 无。Tab5 上有键或者触点按着、这 200 ms 里又没有别的输入报文可发时发一个：按着的还按着（见「按着的时候」） |
| `0x24` | INPUT_MODE | 触摸方式：0 = 触摸，1 = 触摸板 | 无。人在 Tab5 上选的触摸方式（见「触摸方式」）。只发给在 AUTH 的 `caps` 里说了认得它的电脑 |
| `0x25` | TPAD_GAIN | 触摸板方式下光标的加速：手指滑得快时光标最多放大到几倍，单位 0.1 倍，10~50（10 = 不加速） | 无。人在 Tab5 上选的「触摸板加速」（见「触摸方式」）。只发给在 AUTH 的 `caps` 里说了认得它的电脑 |
| `0x26` | PICTURE | 低 8 位：画面不动时的 JPEG 质量 1~100；高 8 位：画面在动时每帧的预算（KB），0 = 不降 | 无。人在 Tab5 上选的画质折成的一组数（见「画质」）。只发给在 AUTH 的 `caps` 里置了 bit2、没置 bit4 的电脑（加档位之前的发送端） |
| `0x27` | PICTURE_MODE | 画质第几档：0 = 最佳画质，1 = 高画质，2 = 均衡，3 = 最佳速度 | `u32`：Tab5 屏幕的帧周期（微秒，实测 15270 上下）。人在 Tab5 上选的画质（见「画质」）。只发给在 AUTH 的 `caps` 里置了 bit4 的电脑 |
| `0x2F` | BYE | 0 | 无。Tab5 这边主动结束（用户退出了显示模式，或者在 Tab5 上暂停了）。**收到它之后发送端不得照原来的地址自动重连**，见「连接过程」。明文还是加密看它排在 AUTH_OK 之前还是之后，见「报文加密」 |

### 键盘

KEY 来自 Tab5 的键盘模块（Tab5 Keyboard，接在机身上的那块，不是 USB 键盘）。

- Tab5 接管屏幕（第一帧上屏）之后才发；键盘没接时不发。
- 每份报文都是完整的按键状态。按键状态每变一次发一份，按先后一份一份地发，不合并。发送端也要按顺序每份都处理，不能只取最新的一份
  （「按下又松开」、同一个键码松开再按下，都是靠中间那一份表达的）。
- 发送端拿每份报文和自己已经注入的状态比，**按集合比**：键码在 6 个位置里的先后没有含义，相邻两份也可能只是先后不同、没有实际差别。
  发送端的初始状态是全松开。Tab5 接管屏幕那一刻已经按着的键不单独报，它会出现在之后的第一份报文里，发送端照常当成新按下；
  报文也可能和发送端当前的状态没有差别（比如接管之前按下、接管之后才松开的键，报上来是全松开）。
- **注入顺序**：先松掉不在这份报文里的键，再把修饰键改成这份报文里的，最后按下新出现的键。
  键帽上印着上档符号的键靠这个顺序：按住 `a` 再按 `!`，报文是 `02 00 04 1E`，先按 `1` 再按 Shift 的话打出来的是 `1`。
- 键盘模块上没有 Shift 键：`Aa` 按住当左 Shift；`Sym` 按住时别的键换成另一层符号，它自己不产生键码；
  键帽上印着上档符号的键（`!` `@` `_` …）发出来是「左 Shift + 对应的键」。
- 两个键可以是同一个键码（`0` 和 `)`、`1` 和 `!`、`-` 和 `_`）。这样的两个键叠着按时，后按的那一下 Tab5 连发两份：
  先一份没有这个键码的，再一份新的。发送端照上面的规则处理就行，不用特殊对待。
- **键码按美式（US）键盘布局给**：键帽上印的字 = 这份报文在 US 布局的主机上打出来的字。发送端把报文**原样按扫描码注入**，主机用 US 布局（约定）。
  主机是别的布局时会打错，比如日文 JIS 布局：`@` 打成 `"`，`(` 打成 `)`，`_` 打成 `=`，`` ` `` 键成了「半角/全角」。
- 键码位置里出现出错标记（`0x01`~`0x03`，HID 规范里「按的键太多，说不清按着哪些」那一类）的报文不代表键松开了：
  发送端让按着的键保持上一份报文的样子，只照它改修饰键。Tab5 的键盘模块最多报 6 个键，现在不会发这种报文。
- **连接结束（不管是哪一方结束的）等于所有键都松开**：Tab5 不会补发一份全松开的报文，发送端要自己把还按着的键放掉。
- Tab5 不做长按连发：一个键按住不放只有按下时那一份 KEY（之后是 HELD，见「按着的时候」）。要连发的话由发送端按主机的设置自己做。
- KBD_LEDS 里 Tab5 现在只用 Caps（亮在键盘模块左边那颗灯上），连接结束时灯灭。发送端在连上之后、以及状态变了的时候发。

### 按着的时候

TOUCH 和 KEY 都只在状态变的时候发：手指按着不动、键按住不放，Tab5 没有新的报文。而发送端要照着 Tab5 上一次报的状态**按时间做事**——
按住的键按主机的设置连发；按着不动的触点隔一阵在原地重报（Windows 规定注入的触点要一直有更新，不然过 1 秒左右被系统收走）。
Tab5 要是这时突然没了（WiFi 断了、死机、重启），它不会说一声，发送端要过 5~11 秒才发现连接断了（见「出错时 Tab5 的做法」最后两条），
这期间它会照着一份过时的状态一直做下去：按住退格时 Tab5 掉线，会多删掉一两百个字。所以：

- **Tab5**：接管屏幕之后，只要它上一份 KEY 里有键按着（修饰键也算）、或者上一份 TOUCH 里有触点，离它上一个输入报文
  （TOUCH / KEY / HELD）满 **200 ms** 就发一个 HELD（它每 20 ms 左右看一次，正忙着解码时会再晚几十毫秒）。
  没有键也没有触点按着的时候不发。说的是发给了发送端的状态：接管屏幕之前按下、之后一直没动的键没报过，不算；从左边缘起手的触点没发过，也不算。
- **发送端**：有键或者触点按着的时候，离上一个输入报文（TOUCH / KEY / HELD，哪一种都算）超过 **700 ms**
  （三个周期多一点），Tab5 报的那份状态就不作数了：
  - 不再连发。按着的键**不松开**：注入「松开」本身有效果（单按一下 Win、Alt 会弹出开始菜单、点亮菜单栏），
    报文要是只是晚到了（丢包重传要 1 秒多），松开再按下还会多打一个字；按着不连发的键什么都不会做。
    之后又收到输入报文就接着连发；键到 Tab5 报它松开、或者连接结束时才松开。
  - 不再重报触点，这几根手指**作废**，它们到抬起之前再报上来的都不算（按着的触点和按住的键一样会一直起作用：
    按在屏幕键盘的退格上、滚动条的箭头上。代价是报文只是晚到的时候这根手指也作废了，要抬起来再按一次）。作废要明着告诉系统（Windows 上是注入一帧带「取消」标记的抬起：
    程序把这次触摸当成没做完，不算点击），不能只是不再重报：实测 Windows 把没人更新的触点收走时，给程序的是一次普通的抬起，等于在那里点了一下。
- **连接结束时**（不管是哪一方结束的）还按着的触点同样是作废，不是抬起：手并没有抬起来，不能在它最后的位置上变成一次点击。键是松开（见「键盘」）。
- HELD 不带内容，发送端不用拿它核对什么，只当作「Tab5 还在，按着的还按着」。

### 触摸方式

电脑桌面上的东西对指尖来说太小，点不准。所以触摸有两种用法，**由人在 Tab5 上选**（设置页上的「触摸板模式」开关，存在 Tab5 里）——
用的时候人在 Tab5 跟前，电脑可能连显示器都没接：

- **触摸**（0，默认）：手指点哪就点哪，电脑把触点照原样注入成触摸。
- **触摸板**（1）：Tab5 的屏幕当一块触摸板，电脑把触点换成鼠标动作（一根手指滑动挪光标、轻点是左键、轻点之后马上再按住滑动是拖动、
  两根手指轻点是右键、两根手指滑动是滚动）。

两种方式下 **Tab5 发的 TOUCH 完全一样**（触点快照、左边缘的退出手势、HELD 都照旧），换成什么是电脑的事；Tab5 只用 INPUT_MODE 告诉电脑现在是哪一种：

- **Tab5**：电脑在 AUTH 的 `caps` 里置了 bit0 才发。握手走完（收到电脑的 READY）之后发一次，排在这条连接的第一个 TOUCH 之前；
  之后设置变了再发，同样排在变了之后的第一个 TOUCH 之前。和别的输入报文不同，它不等接管屏幕（第一个 TOUCH 之前电脑就得知道）。
  那个开关就在 Tab5 的主页面上：连上之后、第一帧到齐之前界面还在屏幕上，人这时拨了 Tab5 当场就发；接管屏幕之后界面停着，
  换方式是左边缘右滑退出显示（Tab5 回到主页面、暂停，见「退出手势」）、拨、点「开始显示」，新连接握手走完时报新的。
  显示期间变只有调试命令（`wd tpad on|off`）做得到。发送端要按连接中途会变来处理。
- **电脑**：每条连接从「触摸」开始，收到 INPUT_MODE 才换（老固件不发，就一直是触摸）；上一条连接上收到的不带到下一条。
  `arg` 不是 0 或 1、带了载荷：断开。收到的方式和现在的一样：什么都不做。不一样：旧方式下按着的先收掉（触摸：按着的触点作废；触摸板：按着的左键松开），
  这时手还按着的那些触点到全部抬起之前都不算——半路接手的话，新方式会把它们当成刚按下的。
- **触摸板的加速**（TPAD_GAIN）：触摸板方式下，手指慢慢滑时光标在 Tab5 的画面上挪得和手指一样远；滑得快时电脑把它放大，
  放大到头是几倍由人在 Tab5 上选（主页面上的「触摸板加速」：关 / 低 / 中 / 高 = 1 / 1.5 / 2 / 3 倍，默认中），Tab5 用 TPAD_GAIN 告诉电脑。
  规矩和 INPUT_MODE 一样：电脑在 AUTH 的 `caps` 里置了 bit1 才发；握手走完发一次（触摸板方式关着也发），之后变了再发，都排在之后的第一个 TOUCH 之前；
  两个都要发时先 INPUT_MODE 后 TPAD_GAIN。电脑每条连接从 2 倍开始，收到才换（没置 bit1、或者 Tab5 是不发它的老固件，就一直是 2 倍）；
  从收到之后的下一个 TOUCH 起按新的算，按着的不用收。`arg` 不在 10~50 之间、带了载荷：断开。多快算快、中间怎么过渡是电脑自己定的。
- 「按着的时候」那几条对两种方式都成立，只有一处不同：触摸板方式下拖动到一半（左键按着）Tab5 没了消息，左键和按着的键一样**不松开**
  （松开就是把拖着的东西放下），到连接结束时才松开。

### 画质

画面压成什么质量、一秒发多少帧是电脑的事，但看画面的人坐在 Tab5 前面，所以选的地方在 Tab5 上：主页面的「画质」，四档。

| 档 | 界面上的名字 | 帧率 | 画面在动时 |
|---|---|---|---|
| 0 | 最佳画质 | 不限 | 不降质量：整屏在动时帧率落到多少算多少 |
| 1 | 高画质 | 限到屏幕刷新率的 1/2（每两次刷新一帧，32.7 帧/秒） | 在这个帧率跟得上的前提下尽量清楚 |
| 2 | 均衡（默认） | 限到屏幕刷新率的 2/3（每三次刷新两帧，43.6 帧/秒） | 同上 |
| 3 | 最佳速度 | 不限：尽量跟上画面源（朝 60 帧/秒靠） | 压到跟得上为止 |

四档画面不动时的质量都一样（C# 发送端是 90）：画面停下来之后总会补到这个质量，各档差的只是动起来的时候。
帧率限在刷新率的整数比上，是因为 Tab5 按屏幕的刷新一帧一帧上屏：限在 30、45 这样的数上，帧和刷新对不齐，隔一阵就多停一拍。

- **Tab5**：电脑在 AUTH 的 `caps` 里置了 bit4 → 发 PICTURE_MODE（第几档 + 屏幕的帧周期）；只置了 bit2 → 发 PICTURE，按下面的表折算；
  两位都没置 → 不发。握手走完发一次，之后设置变了再发。它和画面、触点都没有先后关系。
  显示期间 Tab5 自己的页面不在屏幕上，人要先退出显示才选得到，所以平时就是每条连接开头那一次；协议不限制，连接中途到的（调试命令 `wd pic` 能这样改）照样从下一帧起生效。
  帧周期是 Tab5 量出来的（没量到时给标称值），电脑限帧率的节拍按它算：帧周期 × 2、× 1.5。
  两种屏（ST712x 15.3 毫秒、ILI9881C 20.7 毫秒）都在 5000~50000 微秒里；固件发之前核对，不在范围里（屏幕驱动出了错）就不发 PICTURE_MODE、打一条错误日志，
  电脑按它自己的默认值来——发出去的话电脑会断开，托盘接着重连，一直连不上。

  | 档 | 折成的 PICTURE：质量 | 画面在动时每帧的预算 |
  |---|---|---|
  | 0 最佳画质 | 90 | 0（不降） |
  | 1（高画质） | 90 | 90 KB |
  | 2（均衡） | 90 | 60 KB |
  | 3 最佳速度 | 90 | 30 KB |

  老发送端不限帧率，预算也是固定的，所以只是大致对得上：预算大的档帧率自然低。
- **电脑收到 PICTURE_MODE**：从下一帧起按这一档来。档位不在 0~3、载荷不是 4 字节、帧周期不在 5000~50000 微秒之间：断开。
  PICTURE_MODE 和电脑的第一帧是各发各的，所以每条连接的头一两帧多半还是电脑自己的默认值；托盘程序记着每台 Tab5 上次报的档位，下一条连接从第一帧起就用它。
  限帧率、调预算具体怎么做是电脑自己定的，C# 发送端的做法见「流量控制」里「画面在动时压小」和「限帧率和预算的闭环」。
- **电脑收到 PICTURE**（连的是加档位之前的固件：它的「画质」「动态预算」是两个滑块）：从下一帧起按报的质量和预算压，不限帧率，预算是固定的。
  质量调高了的话，Tab5 上已有的画面是按低的质量压的，和「画面在动时降过质量的地方」一样补一遍；调低了的不用重发。
  质量不在 1~100 之间、带了载荷：断开。预算多大都收（0 = 不降）。
- 两个能力位说的只是「认得这个报文」（收到不会当成不认识的报文断开），照不照着做是电脑的事：托盘程序照着做；
  要固定画质的 `wdsend --quality` / `--motion-kb` 两位都不置，Tab5 就不发；Python 的 `wd_send_test.py` 两位都置、收到只打印（画质是它命令行定死的），
  用来测 Tab5 发得对不对（`--caps 15` 去掉 bit4，看折算出来的 PICTURE）。
- Tab5 主页面上的「性能信息」开关（画面顶上叠一行帧率和延迟）是 Tab5 自己画在帧缓冲上的，电脑不知道，协议里没有它。
  「延迟」是这一帧第一个字节到 Tab5 → 上屏，不含电脑抓屏和编码的时间。

## 认证和加密

要挡的是家里局域网里的另一台设备、或者能看到这段流量的人：旁听画面和键盘输入、冒充 Tab5 或电脑、中途改报文；密码可能很短，
所以抓到握手报文的人不能拿它离线猜密码，在线上也不能想试多少次就试多少次。
不挡：拿到 Tab5 本机的人（闪存没加密）；电脑本身被攻破；从报文的长度和时刻推测内容（报文头不加密，看得出哪个是按键报文、每帧多大）；
局域网里的人捣乱让你用不了（抢着应答询问、占着唯一的连接、反复弹密码框——画面和按键他拿不到）。

用到的算法：SPAKE2（RFC 9382，P-256 / SHA-256 / HKDF / HMAC 那一套）、X25519、HKDF-SHA256、HMAC-SHA256、PBKDF2-HMAC-SHA256、ChaCha20-Poly1305（RFC 8439）。
下面的「报文」指线上的原始字节（8 字节头 + 载荷），`‖` 是字节串相接，引号里的字符串按 ASCII。

### 两边各存什么

- 电脑：自己的编号；由密码算出来的 `w0`（见「配对」，不用存密码本身）；每台配对过的 Tab5 一条 { Tab5 编号、配对密钥（32 字节）、名字 }。
  **改密码 = 清掉所有配对**。
- Tab5：自己的编号；每台配对过的电脑一条 { 电脑编号、配对密钥、名字 }，最多 4 条，满了挤掉最久没连过的。
- 新配出来的配对密钥先只在这条连接里用，**各自核对过对方的 READY 才存下来**，同时换掉同一个对端原来的那条。没走到这一步连接就断了的，不存。
  两边不是同一刻存的（电脑核对完 Tab5 的 READY 就存，这时它自己的 READY 还在路上），所以极少数时候会只存了一边：
  下次连接 Tab5 回 AUTH_UNKNOWN，电脑接着发 PAIR，人在 Tab5 上再输一次密码。
- 改了密码、或者在任何一边移除了一条配对：正连着的那条相关的连接立刻结束（发 BYE）。

### 什么时候可以配对

电脑上设了密码就随时可以配对，不用人在电脑上再点什么：遇到没配对过的 Tab5、或者配对过的 Tab5 回了 AUTH_UNKNOWN，电脑就发 PAIR，
Tab5 上弹出密码框，密码输对了就配上、接着连上。测试工具给了 `--password` 就是「设了密码」。

电脑手里有 `w0`，配对时它那一步不用人动手——对面要是个冒充 Tab5 的程序，每配对一次就能试一个密码。所以电脑给「密码不对」记数，记满了就停止配对：

- **密码不对一次** = 电脑核对出一个 PAIR_REPLY 里的 `cB` 不对。当场记一次，不管这条连接之后怎样；换连接、换 Tab5 都累计。
  PAIR 发出去没等到 PAIR_REPLY 的（超时、断线）不记：对面没拿到任何能验证猜测的东西。
- 记满 10 次，电脑断开、**停止配对**，直到人在电脑上恢复（托盘里点一下，或者重新设密码）；不会过一阵自己恢复。
  停止期间不发 PAIR：没配对过的 Tab5 不连（它们对询问的应答直接不理）；配对过的 Tab5 回了 AUTH_UNKNOWN 就断开。
  配对过的设备不受影响，照常自动发现、自动连接。
- **配对成功**一次、改了密码、人在电脑上恢复配对，次数清零。配对成功 = 配出来的密钥存下来了（握手走完）；密码对上了、后面的握手却断了的不算。
- 次数要存盘，发送端程序重启、电脑重启都不清零。（测试工具不存：每跑一次从 0 记起。）
- 这样冒充 Tab5 的人在人两次恢复之间最多试 10 个密码，拖多久都一样。

Tab5 那一步本来就要人输密码，不用记数：冒充电脑的人每试一个密码都得等人在 Tab5 上输一遍。

### 连上之后走哪条路

```
电脑                                         Tab5
  │ ←──────────── HELLO ───────────────────── │
  │                                            │
  │   有这台 Tab5 的配对密钥：                 │
  │ ───────────── AUTH ─────────────────────→ │
  │ ←──────────── AUTH_OK ─────────────────── │   Tab5 也有同一把
  │ ←──────────── READY（加密）────────────── │
  │ ───────────── READY（加密）─────────────→ │
  │ ───────────── 第一帧 …                     │
  │                                            │
  │   没有，或者 Tab5 回了 AUTH_UNKNOWN        │
  │   （设了密码，没停止配对）：               │
  │ ───────────── PAIR ─────────────────────→ │   弹出密码框，等人输入
  │ ←──────────── PAIR_REPLY ──────────────── │
  │ ───────────── PAIR_OK ──────────────────→ │   （密码不对：电脑再发一个 PAIR）
  │ ───────────── AUTH ─────────────────────→ │   同一条连接上接着走上面那条路
```

1. Tab5 发 HELLO。版本不是 2、帧缓冲或画面的尺寸不是上面的数：电脑断开。
2. 电脑按 HELLO 里的 Tab5 编号查配对（按自动发现的应答去连的，先核对它和应答里的是同一个，见「自动发现」）：有，发 AUTH，走「每次连接」；没有，发 PAIR，走「配对」（没设密码、或者已经停止配对，就不该连它，连上了也只能断开）。
3. Tab5 收到 AUTH：没有这台电脑的配对，或者 AUTH 里的密钥标识和自己存的那把对不上，回 AUTH_UNKNOWN。
   电脑收到后接着发 PAIR（没设密码、或者已经停止配对，就断开）。**电脑不因为收到 AUTH_UNKNOWN 就删掉自己存的配对**（这个报文谁都能伪造），配对成功了才换。
4. Tab5 收到 PAIR 时不管原来有没有这台电脑的配对都照常配对。
5. 配对成功之后在**同一条连接**上接着走「每次连接」：电脑发 AUTH，编号必须是配对时的那个，密钥标识必须是刚配出来的那一把的。
   Tab5 拿这个 AUTH 和刚配出来的那把比（不是和原来存着的比），对不上就断开，不回 AUTH_UNKNOWN；电脑在这时收到 AUTH_UNKNOWN 也断开。

Tab5 每一步只收该来的那种报文，别的一律断开；它发完下面左边这一步之后，电脑的下一个报文要在时限内到齐：

| Tab5 刚做完 | 接着只收 | 时限 |
|---|---|---|
| 发出 HELLO | AUTH 或 PAIR | 5 秒 |
| 发出 AUTH_UNKNOWN | PAIR | 5 秒 |
| 收到 PAIR（弹出密码框，或者标红等人重输） | 什么都不该来：这期间电脑发了东西就断开；连接断了就关掉密码框 | 从弹出 / 标红起 2 分钟没输完就关掉密码框、断开（不发 BYE），回到等连接 |
| 发出 PAIR_REPLY | PAIR_OK 或 PAIR | 5 秒 |
| 收到 PAIR_OK（`cA` 对，关掉密码框） | AUTH（编号同配对时的，密钥标识是刚配出来那一把的） | 5 秒 |
| 发出 AUTH_OK 和 READY | READY（加密） | 5 秒 |
| 收到 READY | 和平时一样：STRIP、PRESENT、KBD_LEDS、BYE（发送端可以在第一帧之前发 KBD_LEDS） | 5 秒内要收到第一帧的 PRESENT |

密码框到时间不算人拒绝，所以不发 BYE：电脑过一会儿会再连上来，密码框再弹出来——Tab5 没暂停时本来就是在等连接，
人不在跟前时弹着也无妨（Tab5 到时间照常息屏，息屏时框收起来；再亮屏时那一次询问还没答完的话框再弹出来）。人点了取消才发 BYE（见「配对」末尾）。

电脑这边也是每一步只收该来的，别的一律断开：

| 电脑刚做完 | 接着只收 | 时限 |
|---|---|---|
| 连上 | HELLO | 5 秒 |
| 发出 AUTH | AUTH_OK、AUTH_UNKNOWN，或者明文的 BYE（`0x2F`） | 5 秒 |
| 收到 AUTH_OK | READY（加密） | 5 秒 |
| 发出 PAIR | PAIR_REPLY，或者明文的 BYE | 130 秒（比 Tab5 密码框的 2 分钟略长，正常是 Tab5 先放弃） |
| 发出 PAIR_OK 和紧跟的 AUTH | AUTH_OK，或者明文的 BYE（这时来 AUTH_UNKNOWN 算不守协议） | 5 秒 |

电脑同样检查 `flags` 是 0、握手报文的 `arg` 是 0（HELLO 的 `arg` 是版本号）、长度是表里的定长，不是就断开。
握手期间收到 BYE 按「Tab5 上的人结束了」处理（见「连接过程」）；等不到该来的报文就断开。

### 配对

电脑是 SPAKE2 里的 A，Tab5 是 B。密码 1~64 个字符；Tab5 上用屏幕软键盘输入，只打得出 ASCII 的可打印字符（`0x20`~`0x7E`），
输入框最多收 64 个，所以电脑那边设密码时只收这些字符、最多 64 个。

```
w0 = PBKDF2-HMAC-SHA256(密码的字节, 盐 = "Tab5 WinDisplay v2 password", 10000 次, 输出 40 字节)
w  = (w0 按大端当成整数) mod n                                  n 是 P-256 的阶
M  = 02886e2f97ace46e55ba9dd7242579f2993b64e16ef3dcab95afd497333d8fa12f      RFC 9382 给 P-256 定的两个点（压缩格式）
N  = 03d8bbd6c639c62937b04d997f38c3770719c629d7014d49a24b4f98baa1292b49
```

（PBKDF2 在这里的用处只是让电脑上存的 `w0` 不是密码本身；猜密码的人被挡在 SPAKE2 和上面的次数上限那里，不是被它挡住的。）

1. 电脑取随机数 `x`（1 ≤ x < n），算 `pA = x·G + w·M`，发 PAIR。
2. Tab5 先检查 `pA`（不合格就断开，不弹密码框），然后弹出密码框等人输入。输完后算 `w`，取随机数 `y`（1 ≤ y < n），
   算 `pB = y·G + w·N`、`K = y·(pA − w·M)`，照下面的式子算出 `cB`，发 PAIR_REPLY。
3. 电脑算 `K = x·(pB − w·N)`，核对 `cB`：
   - 对：发 PAIR_OK（`cA`），接着发 AUTH。
   - 不对（Tab5 上输的密码和电脑的不一样）：记一次；没记满就换一个新的 `x` 再发一个 PAIR，记满了就断开、停止配对（见「什么时候可以配对」）。
     Tab5 在发了 PAIR_REPLY 之后又收到 PAIR，就知道刚才的密码不对：密码框标红、清空，等人重输，回到第 2 步。
4. Tab5 收到 PAIR_OK，核对 `cA`：不对就断开（密码对而 `cA` 不对，对面不是照本协议实现的）。

```
A = 电脑编号，B = Tab5 编号                                      各 16 字节
TT = len(A) ‖ A ‖ len(B) ‖ B ‖ len(pA) ‖ pA ‖ len(pB) ‖ pB ‖ len(K) ‖ K ‖ len(w) ‖ w
       len() 是 8 字节小端的字节数；pA、pB、K 是 65 字节的非压缩格式（04 ‖ X ‖ Y）；w 是 32 字节大端
Ke ‖ Ka   = SHA-256(TT)                                          各 16 字节
AAD       = SHA-256(HELLO 报文 ‖ 这一次的 PAIR 报文)
KcA ‖ KcB = HKDF-SHA256(IKM = Ka, 盐 = 空, info = "ConfirmationKeys" ‖ AAD, 输出 32 字节)        各 16 字节
cA = HMAC-SHA256(KcA, TT)        cB = HMAC-SHA256(KcB, TT)
配对密钥  = HKDF-SHA256(IKM = Ke, 盐 = 空, info = "Tab5 WinDisplay v2 pairing key", 输出 32 字节)
```

必须做的检查：

- 收到的 `pA` / `pB` 是 65 字节、以 `04` 开头、在曲线上，不是就断开；`K` 是无穷远点就断开；
- `x`、`y` 每次重新取，绝不重复使用；
- 比较 `cA` / `cB` 用的时间不随内容变化；
- 标量乘法里的标量（`x`、`y`、`w`）是秘密，要用带防护的乘法（mbedtls：`mbedtls_ecp_mul` 并给随机数源；`mbedtls_ecp_muladd` 不防旁路，
  只能拿来做不带秘密标量的点加减）。电脑这边（C#，BouncyCastle）：`w·M`、`w·N` 由 `w0` 算好留着，配对时不再拿 `w` 做乘法；
  `x·G` 和这两个都是定点的乘法，用定点梳状乘法（`FixedPointCombMultiplier`）；`x·(pB − w·N)` 把 `x` 加上一两个 `n` 垫成固定的 257 位、
  走蒙哥马利阶梯，不用库里默认的窗口法。`x` 每次配对只用一次，从网络上量时间本来就难，电脑这边做到这一步为止。

Tab5 的密码框：标题里带上电脑报的名字；这台电脑的编号已经配对过的，标题写「重新配对」（平时不该再问，让人多看一眼）；
`cA` 核对通过就关掉；点取消等于暂停（发 BYE、不再监听，到主页面上点「开始显示」才接着等）。
密码框不属于哪一页：Tab5 的界面在哪一页都弹；息屏着的话先亮屏。

### 每次连接

```
密钥标识 = HMAC-SHA256(配对密钥, "Tab5 WinDisplay v2 key id") 的前 8 字节
```

1. 电脑取一次性的 X25519 密钥对，发 AUTH（里面带它存的这把配对密钥的标识）。
2. Tab5 查这台电脑的配对：没有、或者标识对不上，回 AUTH_UNKNOWN。对得上：取自己的一次性密钥对，发 AUTH_OK 和紧跟的 READY（加密），两个一次发出、中间不插别的。
3. 电脑算出会话密钥，核对 READY 的认证码。对不上：断开，什么都不再发（按认证没过处理，见「什么时候可以配对」）。对上了：发自己的 READY（加密）。
4. Tab5 核对电脑的 READY，对不上就断开。到这里两边都确认了对方有配对密钥。

```
dh  = X25519(自己的一次性私钥, 对方的一次性公钥)                 32 字节；全 0 就断开
th  = SHA-256(HELLO 报文 ‖ AUTH 报文 ‖ AUTH_OK 报文)             AUTH 是被这个 AUTH_OK 应答的那一个
okm = HKDF-SHA256(IKM = dh, 盐 = 配对密钥, info = "Tab5 WinDisplay v2 session" ‖ th, 输出 64 字节)
电脑 → Tab5 方向的密钥 = okm 的前 32 字节        Tab5 → 电脑方向的密钥 = okm 的后 32 字节
```

一次性密钥对每条连接重新取，不能重复使用（新鲜全靠它：别人把旧的 AUTH 或 AUTH_OK 重放过来，对不上这次新取的那一半，READY 就过不了）。
握手里的编号、名字、能力位、尺寸都进了 `th`（配对时进了 `AAD`），中途被人改过的话两边算出来的密钥不一样，READY（配对时是 `cA` / `cB`）就对不上。
认证通过之后，两边各自把对方这次报的名字记进配对里。

密钥标识是给「两边存的不是同一把」留的出路：比如重新配对时最后一步断了，一边换成了新的、另一边还是旧的。没有它的话电脑每次都认证失败、
Tab5 又不会说 AUTH_UNKNOWN，两边就永远对不上了。标识只有 8 字节，从它推不出密钥。

带一次性密钥交换是为了：配对密钥以后万一泄露，以前录下来的流量也解不开。

### 报文加密

- **哪一刻开始**，以 TCP 上的先后为准，只有这一条规则：Tab5 发的报文，AUTH_OK 以及它之前的是明文，AUTH_OK 之后的全部加密；
  电脑发的报文，收到 AUTH_OK 之前发的是明文，之后发的全部加密。每个方向的第一个加密报文必须是 READY。
- 所以 Tab5 的 BYE（`0x2F`）两种都可能：发 AUTH_OK 之前要结束（人在密码框上点了取消），是明文的；之后是加密的，
  而且排在 READY 后面（AUTH_OK 和 READY 是一次发出的）。电脑收到 AUTH_OK 之后的第一个加密报文不是 READY，按不守协议断开。
  电脑在收到 AUTH_OK 之前要结束，直接关连接。
- ChaCha20-Poly1305：密钥 = 这个方向的会话密钥；nonce（12 字节）= 4 字节 0 ‖ 这个方向的报文计数（`u64` 小端；READY 是 0，之后每个报文加 1）；
  附加数据 = 8 字节报文头；明文 = 载荷。线上是 头 ‖ 密文 ‖ 16 字节认证码，没有载荷的报文也带认证码。
- 收的一方：报文头一到照常先检查（类型、长度上限），再收密文。**认证码对上之前，解出来的内容不能用**（Tab5 边收边解密、收完核对，
  对上了才去检查 JPEG 文件头、交给解码器）。任何一个报文认证不过就断开：重放、丢了一个、换了顺序、改了头或内容，都落在这一条上。

## 流量控制

发送端限制「已发出 PRESENT、还没收到 ACK」的帧数：

- **平时保持 2 帧在途**：在途的不到 2 帧就可以发下一帧，不用等 ACK。Tab5 收完一帧要解码、等屏幕的帧边界翻页才回 ACK，这段时间下一帧已经在路上了。
- 到了 2 帧就等 ACK。**最早在途的那一帧**迟迟等不到 ACK，就接着发，最多 **4 帧**在途；到了 4 帧只能等。
  「迟迟」= 从那一帧发出算起，超过 **60 ms** 和「最近十几帧往返时间的中位数 × 2」里大的那个：画面重、每帧本来就要一百多毫秒的时候不算迟到，不往路上多压帧
  （两帧在途时每帧的往返里含排在前一帧后面的时间，中位数量出来就是这样的，不用另外折算）。
  开头几帧往返时间还没摸准（比如收到的 ACK 不到 4 个）时不算迟到。门限从最早那一帧算起，所以一迟到会连着放到 4 帧，不是放一帧再等一个门限。
- **跟得上画面源的时候可以多放一帧**（3 帧在途），不等 ACK：发送端最近 0.5 秒之内「跟上过画面源」才行，见下面「跟得上画面源时多放一帧」。
- ACK 按 PRESENT 的先后回来，一个 ACK 对应一帧。

等 ACK 期间画面又变了，发送端不排队，只保留最新的画面，轮到发的时候再编码。这样 Tab5 或网络来不及时掉的是帧率，延迟不会越积越多。

**为什么是 2 帧。** 只留 1 帧时，Tab5 解码和等翻页的那十几二十毫秒链路是空着的。实测（2026-11-13，`tools/wd_send_test.py --inflight N` 对真机，
Tab5 固件带下文说的 lwIP 配置：收包邮箱 64、乱序队列 12、SACK、TCP 定时器间隔 50 ms；三栏都是 ACK 迟到时最多放到 4 帧；每格两轮，帧/秒；18 轮都没有超过 500 ms 的停顿，相邻两帧发出的间隔最长的一次是 461 ms，在整屏滚动、平时 2 帧的第二轮）：

| 画面（每帧大小） | 平时 1 帧 | 平时 2 帧 | 平时 3 帧 |
|---|---|---|---|
| 测试卡，局部更新（15 KB） | 45.7 / 47.0 | 64.2 / 64.1 | 64.9 / 65.2 |
| 整屏滚动（47 KB） | 29.9 / 30.3 | 41.7 / 41.0 | 35.2 / 34.1 |
| 噪点（431 KB） | 7.6 / 7.7 | 9.0 / 8.8 | 8.9 / 8.9 |

3 帧不比 2 帧快（整屏滚动还慢一截，原因没查），画面还多晚一帧。2 帧的代价是每帧多等前面那一帧处理完，发出到 ACK 的中位数：
测试卡 13 → 26 ms、整屏滚动 24 → 40 ms、噪点 117 → 211 ms（3 帧时是 42 / 84 / 324 ms）。
只有画面连着变的时候才有第 2 帧在路上；点一下、打一个字这种单独的一帧照旧马上发、马上上屏。

Windows 真屏幕（同一天，C# 发送端 `wdsend auto --screen`，1920×1080 的桌面上开一个全屏动画，每帧 138 KB；`--inflight 1` 和默认交替各两轮，每轮 27 秒）：
15.9 / 15.5 → **20.8 / 20.4 帧/秒**，发出到 ACK 的中位数 50 → 61~62 ms，四轮都没有超过 500 ms 的停顿（相邻两帧发出的最大间隔 117 / 207 ms 对 242 / 176 ms）。
提得没有整屏滚动多：这种画面一帧就比两个 64K 的接收窗口还大，而那时的 Tab5 解码、等翻页的时候不读套接字，在路上的第 2 帧这段时间只能先进来一个窗口。

**2026-11-14 重新量过（Tab5 改成等翻页时接着收之后，上面两张表是改之前的固件）。** 结论没变，还是 2 帧。整屏滚动、每帧约 40 KB：
`tools/wd_send_test.py` 2 帧 55.7、3 帧 62.1 帧/秒；C# 发送端生成的滚动画面 2 帧 58~60、3 帧 62.7；Windows 真屏幕上 60 帧/秒的全屏动画
（C# 抓屏，画面在动时压到每帧 39 KB）2 帧 **57.5**、3 帧 58.6 帧/秒，发出到 ACK 的中位数 26.8 / 29.8 ms（生成画面是 29 / 44 ms）。
3 帧只多一两帧，面板一秒也只刷 65 次，不值得多晚一帧。每帧 47 KB 时 3 帧反而略慢（54.4 对 53.2）。

**跟得上画面源时多放一帧（2026-11-15，发送端的做法，协议不管）。** 平时 2 帧在途对每秒 60 幅的画面源差一口气：Tab5 按屏幕的刷新（15.3 ms 一次）一帧一帧上屏，
哪一帧晚到几毫秒、错过一次刷新，后面的帧都跟着晚一个刷新周期，要靠屏幕比画面源快的那一点（每帧 1.4 ms）十来帧才追得回来。这期间 ACK 都晚
（往返从 27 ms 到 45 ms 上下），只许 2 帧在途的话新抓到的那一幅只能等，等的时候再来一幅它就被顶掉。实测全屏动画每分钟被顶掉一两百幅（2~3 帧/秒），几乎每次都是这样来的。
做法（`sender/` 的 `FlowControl`）：发送端可以发了、画面源却还没出新的一幅，它就等画面源；等完时在途的不到 2 帧，这一帧算「等来的」。
**连着 3 帧都是等来的 = 跟上了画面源**；离上一次跟上不到 **0.5 秒**时，在途 2 帧还可以再发 1 帧。晚的那一段排在 Tab5 的接收窗口里，不丢，追回来之后在途的自己落回 1~2 帧。
画面源比管线快的时候（重的帧）发送端从来不用等画面源，过了 0.5 秒就回到 2 帧在途，延迟不涨。
- 为什么要「连着 3 帧」：画面源自己不匀时（隔几帧少出一幅），管线比它慢也会偶尔等到它一次。只看一次的那一版，每帧 70 KB（Tab5 只跟得上 43 帧/秒）时
  35%~60% 的帧是 3 帧在途发的，往返中位 42 → 45~51 ms、95% 53 → 70 ms，帧率不涨。
- 为什么要「等完时在途的不到 2 帧」：靠多放的那一帧才腾出手来等画面源的，只说明还撑得住，不说明追回来了。
- 代价：画面本来停着、或者只是零星地变（打字、光标），「跟上」的时刻一直在更新；接着来一段 Tab5 跟不上的重画面，开头 0.5 秒是 3 帧在途。
  拖一下窗口、滚一下滚轮这种不到 0.5 秒的，整段都多晚一帧（每帧 70 KB 时约 24 ms），帧率不涨。只在 Tab5 是瓶颈时才有（动态预算调大了、或者关了）；
  默认的 40 KB 预算下 Tab5 跟得上，多放的那一帧不排队。

实测（Windows 真屏幕上 60 帧/秒的全屏动画，场景带 `--gpu 10`，C# 抓屏，每轮 60 秒；「关」= `--spare-hold 0`；同一时段交替跑）：

| 画面（每帧大小） | 帧/秒，关 → 开 | 没读就被顶掉的（幅 / 分钟） | 发出到 ACK 中位 | 95% | 3 帧在途发的帧 |

（第二行那三轮里系统自己每分钟还少交 90~100 幅给抓屏，所以到不了 59；前一轮系统不少交的时候是 57.9 / 57.8 → 59.2 / 59.3。）

链路每秒 3 MB 上下，所以整屏都在变的一帧要在 40 KB 上下才跟得上面板。同一个全屏动画（质量 60 时每帧 69.5 KB）：改之前 32.7 帧/秒；
Tab5 改了、发送端不压小 44.1；再把在动的帧压到 39 KB（质量平均 29）57.5。
C# 发送端的做法（`sender/` 的 `StripEncoder`）：变了的行超过四分之一屏的帧按「每帧不超过预算（多少由画质的档位定，见下一段；连的是老固件时用它报的固定值，都没有时默认 40 KB）」定 JPEG 质量，上一帧超了这一帧就往下调（默认不低于 20），
小了再往回升；只变了一小块的帧照原质量。画面不再大片地动了（150 ms 没出过在动的帧；不等「抓屏说画面没变」：整屏停了、还有一小块动图一直在变的画面等不到它）之后，
把降过质量的条带按原质量补发一遍（和那一帧变了的条带放在同一帧里）。这些都是合规的普通帧，Tab5 不知道也不用知道。
质量要在量化步长上按比例调，不能按质量数的百分比调：质量 93 → 82 步长是 2.6 倍，直接调会在预算两边隔帧来回跳（实测过）。

**限帧率和预算的闭环（发送端的做法，协议不管）。** 画质的档位（见「画质」）定两件事，C# 发送端这样做（`sender/` 的 `PictureMode.cs`、`BudgetControl.cs`、`DisplaySession.cs`）：

- **限帧率**（高画质、均衡两档）：发帧按节拍走，一拍 = Tab5 报的帧周期 × 2 或 × 1.5。流量控制放行了、拍子还没到就等到拍子再取画面（取的是那一刻最新的一幅）；
  偶尔晚了不到一拍的，后面还按原来的节拍；晚了一拍以上的不补。Windows 上显示期间把进程的定时精度提到 1 毫秒（默认 15.6 毫秒，卡不准 22.9 / 30.6 毫秒的拍子）。
- **预算**（高画质、均衡、最佳速度三档）：每一档有起点和范围（高画质：80 KB 起，30~160；均衡：50 KB 起，20~110；最佳速度：28 KB 起，20~60），在范围里闭环找「跟得上的前提下最大的数」。
  「跟得上」看的是每一帧发出的时候：它是等来的（等下一拍，或者等画面源出新画面），等完时在途的不到平时的帧数。
  每半秒看一次在动的帧里没跟上的占多少：连着两个半秒都占到四分之一就降（× 0.85，第二个半秒占到六成 × 0.7）——只有一个半秒的不算，
  无线上隔一阵就有一次几十毫秒的停顿，不值得为它降；刚升了一步（5 秒之内）就站不住的不用等，一个半秒就退回升之前的数
  （停顿正好落在这 5 秒里也会退这一步：分不出来，退的只是 6%）。降了之后、连接开头的半秒不看
  （在途的帧还是按旧预算发的；连接刚起来时 Tab5 在接管屏幕，头几帧的确认要一百多毫秒）。不到 5%、离上次调过了两秒、而且这半秒的帧把预算用满了，就升 6%。
  降的时候记下「在这个数上站不住」，半分钟里不往它那儿升，过了再试一次；一试又站不住，下一次隔得加倍（最长 4 分钟）——不然稳态就是来回摆，每摆一次画面卡一下。
  画面简单、按原质量压出来也到不了预算的时候不升：那时跟得上说明不了预算再大也跟得上。
  预算每调一次，编码器在动时的质量跟着挪一步（平时它在预算的 85%~105% 之间不动，不跟的话帧的大小不随预算变）。
- **在途的帧数**：均衡档平时 3 帧在途（别的档 2 帧，见上面「流量控制」）。Tab5 一帧从发出到确认，除了接收还要 31 毫秒上下（解码 13.7 + 等屏幕刷新上屏约 15 + 来回），
  平时 2 帧在途等于要求它不超过两拍：高画质档两拍 61 毫秒，够每帧七八十 KB；均衡档两拍只有 45.8 毫秒，实测预算只站得住 34 KB，比不限帧率的时候还糊。
  Tab5 那头是接收、解码、等上屏三段流水，三帧各占一段并不排队，所以均衡档放到 3 帧。
- **换档**：连接中途 Tab5 报了另一档，下一帧起节拍、预算、在途的帧数都按新的一档从头起。报的还是原来那一档、只是帧周期不一样
  （Tab5 每次量出来差几微秒；托盘记着的是上一条连接报的），只换节拍的周期，预算接着用闭环已经找到的数。
- 最佳速度一档下，画面源比 Tab5 快（Tab5 解一帧 4:2:2 的整屏要 13.7 ms，一拍只有 15.3 ms）的时候，帧帧都算没跟上，预算停在下限 20 KB：
  这一档就是拿清晰度换帧率。画面源慢一些（看视频，24 / 30 幅）就跟得上，预算会往上走。
- 实测（2026-11-15，`wdsend --pattern scroll --detail 0.04`：整屏滚动、按质量 90 压一帧 180 KB 上下的重画面，各 90 秒；日志 `firmware/tools/dispbench/logs/b3e_*`、`b3b_t3d_*`）：

**对接收端的要求。** 平时 2 帧在途（跟得上画面源时 3 帧）、迟到时放到 4 帧，是按接收端满足下面两条定的（Tab5 固件，或者别的实现，都一样）：

1. **TCP 接收窗口被顶满时不丢数据。** 两帧加起来比 64K 的窗口大是常事，发送端会一直把窗口顶满。Tab5 固件靠 lwIP 的三项配置做到：
   每条连接的收包邮箱 64、乱序队列 12 个包、开 SACK（`firmware/sdkconfig.defaults`）。没有这三项的固件窗口一满就丢段、丢了又补不快：实测 2 帧在途、满了死等时偶尔卡 1~1.7 秒、个别轮次帧率掉一半；
   3 帧在途时塌到 2.6 / 6.2 帧/秒然后断开（`lwipB_summary.txt` 的 base 一栏）。本节的发送端迟到时会放到 4 帧，没在那样的固件上量过，不要对它用。
2. **自己发的小报文丢了之后重传得快。** 发送端多发的那几帧只救得回四次里的三次（见下一段），剩下的靠接收端的 TCP 重传超时——它有多长，画面最坏就停多久。
   Tab5 固件把 lwIP 的 TCP 定时器间隔配成 50 ms（同一个文件），超时重传在 0.23~0.5 秒；lwIP 默认的 250 ms 是 1.1~2.5 秒。

这两条现在不在握手里协商（HELLO 的 `caps` 里没有对应的位），靠发送端和固件一起更新来保证。

**为什么 ACK 迟到了要接着发。** Tab5 发回的 ACK 加上认证码只有 44 字节，这种小包在上行丢的比例实测千分之四上下。丢了之后 TCP 按序交付，
后面到的 ACK 发送端的程序也读不到；Tab5 的 TCP（lwIP）要收到 **3 个重复确认**才立刻重传，否则等自己的重传超时。
重复确认是发送端的 TCP 每收到 Tab5 后面发来的一个段回一个，所以丢的那个 ACK 之后 Tab5 还得再确认 3 帧：在途的另一帧，加上迟到之后多发的两帧——这就是上限取 4 的原因。
抓包逐次数过（2026-11-13，整屏滚动 4 × 3000 帧，丢了 52 次）：39 次这样在 0.07~0.32 秒补上；13 次凑不够 3 个，只能等 Tab5 的重传超时。
凑不够的原因（lwIP 只认不带数据、通告窗口没变的确认）：发送端的系统那一刻通告的窗口正好在变 4 次，重复确认搭在数据包上发出去了 3 次，
连着丢了两个 4 次，连接刚开头、往返时间还没摸准所以没多发 1 次，下行同时在丢包、多发的两帧没及时到 1 次。
这个超时 lwIP 默认配置下是 1.1~2.5 秒，TCP 定时器间隔配成 50 ms 之后是 0.23~0.5 秒（上面第 2 条）。两样都有之后：

|---|---|---|---|---|

## 声音

电脑上正在放的声音送到 Tab5 的扬声器（或者耳机口）。和画面、输入走同一条连接，报文照常逐个加密。

- **格式定死**：48 kHz、双声道、16 位小端 PCM，不压缩（约 1.5 Mbps，比画面小一个数量级）。别的采样率 / 声道数由电脑转好再发。
- **AUDIO（`0x40`）**：`arg` 填 0，载荷是一段连续的采样，左右交替，长度是 4 的倍数、4~3840 字节（最多 20 ms）；建议 10 ms 一段（1920 字节）。
  相邻两个 AUDIO 的采样在时间上是接着的，报文里**没有时间戳**。
- **什么时候可以发**：HELLO 的 `caps` bit0 置了位，握手走完（电脑发出 READY）之后随时可以发，第一帧上屏之前也行。
  AUDIO 不算一帧、Tab5 不回 ACK、不占流量控制的在途帧数；「握手走完 5 秒内发完第一帧」的期限也不因为它往后挪。
- **不能让画面挡住声音**。一帧画面有几十上百 KB，整帧一口气交给系统的话，这段时间里到点的声音都排在它后面。
  发送端要一个条带一个条带地发，每个条带（和 PRESENT）之前先把已经到点的声音发掉；没在发画面的时候声音到点就发。
  报文是逐个加密的，打包的先后必须就是发出的先后——声音和画面由两个线程产生的话，共用一把发送锁。
- **连接堵住时不攒**。到点了发不出去的声音，发送端最多留 200 ms，再多就扔掉最旧的：延迟不往上积。
- **电脑没有声音时不用发**（发全 0 的也行，Tab5 一样放）。Tab5 握手走完就把 codec（ES8388）和扬声器功放打开预备着，没有声音时自己放静音，到连接结束才关
  （功放平时关着，开关的先后见 `firmware/main/wd_audio.hpp`：这样 codec 上电、时钟起停的瞬变不会从扬声器放出来；等第一段声音到了才开的话，它的开头约 0.15 秒出不了声）。
- **音量在 Tab5 上**（主页面的「音量」，0~100，0 = 静音），不跟电脑的系统音量；电脑本机照常出声，发送端不动电脑的声音设置。

**Tab5 怎么放。** 没有时间戳，也不做音画对齐，按到的先后放，中间隔一小段缓冲（定的口径：延迟低优先，偶尔断一下可以接受）：

- 攒到「起播缓冲」（默认 50 ms）开始放；没攒够、但已经 250 ms 没有新的到，也放（一段声音的结尾、很短的提示音，不留在缓冲里；250 ms 比链路一次停顿长，停顿当中补来的一点点不会被提前放掉）；
- 放空了（链路停了一下，或者电脑那边的声音停了）就重新攒到起播缓冲再放。放空之后 0.5 秒之内又接上的算一次**断音**；
  放空之前那一小段是纯静音的听不出来，不算；隔得更久的多半是声音自己停了又来了一段，也不算断音，`wd` 里单独记个数；
- 链路停完之后会一口气补来一大段：缓冲里超过「起播缓冲 + 80 ms」就把最旧的扔掉、回到起播缓冲。没超过的就留着，
  所以停过一次之后缓冲比起播时深一些（延迟最多到 130 ms），下一次同样长的停顿就盖得住；
- 电脑和 Tab5 的采样时钟差几十 ppm，缓冲会很慢地涨或者落，最后也落在上面两条上：十几分钟断一下或者跳一下。
- Tab5 的扬声器是单声道的，只接了 codec 的左声道输出：没插耳机时左右两路混成一路放，插着耳机时原样放立体声。

**实测**（2026-11-14，真机，2.4G；链路本身隔几秒整个停 30~200 ms，断音就是它造成的）。
「断音」是 Tab5 自己数的（调试命令 `wd`），口径见上面「Tab5 怎么放」（下表是口径收紧之前量的：那时放空之后 2 秒之内接上的都算，测的是连续的正弦波，两种口径数出来一样）。
`wd` 里另有一项「I2S 欠载」：播放任务往 I2S 写晚了、I2S 自己补了约 2.7 ms 的静音，缓冲并没有放空，不在断音里。每格一轮约 60 秒，`tools/wd_send_test.py --tone 1000`：

| 起播缓冲 | 整屏滚动（79 KB/帧，32 帧/秒） | 画面几乎不动（2 帧/秒） |
|---|---|---|
| 30 ms | 断音 10 次，合计 410 ms，最长 100 ms | 2 次，合计 70 ms |
| 50 ms（默认） | 4 次，合计 270 ms，最长 100 ms | 1 次，合计 20 ms |
| 100 ms | 2 次，合计 190 ms，最长 100 ms | 0 次 |

加声音前后帧率一样。Windows 抓屏 + 抓系统声音、屏幕上是游戏那样的场景（69 KB/帧，32 帧/秒）120 秒：断音 5 次，合计 190 ms，最长 60 ms；
发送端没有因为连接堵住扔掉过声音。全部数字和各项怎么测的在 `firmware/tools/dispbench/logs/sound1_summary.txt`。

口径收紧、补尾巴加上之后（起播缓冲 50 ms）又量了几轮：整屏滚动（79 KB/帧，32.2 帧/秒）62 秒断音 2 次，合计 110 ms，最长 60 ms，I2S 欠载 0 次
（补尾巴的时限还是 50 ms 的那一版量过两轮：8 次合计 440 ms、3 次合计 110 ms——链路好坏每一轮差得很多，数字只能看量级）。

30 ms 的短音放掉了（收到 30 ms、放出 30 ms、缓冲里 0）；停 0.3 秒记一次断音（310 ms），停 0.8 秒记在「隔了 0.5 秒以上才接上」里。

## Tab5 怎么处理三块帧缓冲

面板有三块帧缓冲轮流用（2026-11-15 起；之前是两块）：一块正在扫出，解码写另一块，一帧的条带都解完（PRESENT）就登记翻页，在下一个帧边界生效。
每一块轮到解码往里写的时候，里面还是往前数第三帧的画面，缺的是中间两帧的条带。Tab5 把那两帧的压缩数据留着，能不补就不补：

- 新一帧的条带完全盖住了前两帧的某个条带：那个条带不用补（整屏都在变的画面因此每帧只解一遍）；
- 只盖住一部分：先把老的那个条带补上（两帧都有的话先补更老的），再解新条带；
- 到 PRESENT 时还没被盖住的：翻页之前全部补上，也是老的在先。

**翻页不挡着收下一帧、也不挡着解下一帧。** PRESENT 到了、这一帧解完：

- 前一帧的翻页已经生效了：马上登记这一帧的翻页，不等它在帧边界生效，下一帧的条带接着往空着的那一块里解；
- 前一帧的翻页还没生效：同一时刻只能有一次没生效的翻页，这一帧先放着。这时三块都不能写（一块在扫出，一块等着上屏，一块是放着的这一帧），
  后面到的条带照收、照解密，攒着不解码（大条带是这样；不到 2 KB 的小条带是在收的那个任务里解密的，轮到它时先等帧边界再读它的载荷——局部更新的帧本来就赶得上，不靠这个）；
  前一帧的翻页一生效，登记这一帧、把攒下的条带排去解码。

每一帧的翻页生效时回它的 ACK（所以 ACK 的含义没变：这一帧已经上屏；`present_us` 仍是收到 PRESENT 到换上屏幕）。

为什么要这样：面板 65.4 Hz，帧周期 15.3 ms，接收端每帧的活（收、解密、解码、等帧边界）只要有一段必须排在帧边界之后才能开工，加起来就容易比一个帧周期长，帧率锁在刷新率的几分之几上。走过三版：

| 固件 | 做法 | 整屏在动时卡在哪 |
|---|---|---|
| 最早 | 两块帧缓冲；登记翻页之后停下来等帧边界，生效了才读下一帧 | 「回 ACK + 收 + 解码 11 ms」比一个帧周期略长：每两个帧周期一帧，锁在 32.7 帧/秒，每帧再小也一样（47 KB 和 79 KB 都是 32.x） |
| 2026-11-14 | 两块；等帧边界时接着收、接着解密，条带攒着，翻页生效了才解码 | RGB565（4:2:0，解一帧 11 ms）时 55~62 帧/秒；改走 YUV422（4:2:2，解一帧 13.8 ms）之后离一个帧周期只差 1.5 ms，帧稍大就隔一帧错过一次刷新：锁在 43.6（刷新率的 2/3） |
| 2026-11-15 | 三块；一帧解完不等前一帧的翻页生效，接着解下一帧 | 解一帧比帧周期短就跟得上：同一个场景（整屏滚动，每帧 34.7 KB，YUV422）42.8 → 60.1 帧/秒，发出到确认的中位数 42.4 → 27.7 ms |

（第三版的对照：`wd_stutter.sh … --pattern scroll --seconds 30 --send "--detail 0.10"`，最佳速度档，日志 `logs/b4g_a1_*`（两块）、`logs/b5_a1_*`（三块）。）
补解有没有补对，报文和统计里看不出来（补错了只是屏幕上露出旧画面），用 `firmware/tools/dispbench/wd_catchup_check.sh` 查：
发一串随机的局部更新、每帧换一种条带高，停住，经 JTAG 读出正在扫出的那块帧缓冲，和发出去的最后一帧逐块比。

发送端不用管这件事，只要保证：**每一帧里的条带互不重叠**。条带的划分尽量每帧一致（比如固定每 160 行一条），
这样上面第一种情况最多，Tab5 最省事。

## 连接过程

1. 发送端连上 → Tab5 发 HELLO。
2. 握手（见「认证和加密」）：没配对过的先配对，然后互相认证、换出会话密钥，两边各发一个 READY。
3. 发送端发第一帧。**第一帧必须覆盖整屏**（1280 行都要有条带），而且**发出 READY 之后 5 秒内要发完**（从 Tab5 收到 READY 算起，到它收到第一帧的 PRESENT）。
   第一帧到齐之前屏幕上一直是 Tab5 自己的界面（配对时多一个密码框），到齐了 Tab5 才接管屏幕、把它显示出来。
4. 之后按上面的流量控制循环。任何一方发 BYE 或断开连接即结束，Tab5 回到自己的界面。

**退出手势。** 显示期间触摸都转给了发送端，Tab5 自己只认一个手势：从屏幕左边缘（32 像素以内）起手向右滑（0.8 秒之内划过 250 像素），
Tab5 发 BYE、不再监听，屏幕回到主页面（暂停：不接受连接，人可以改触摸方式这些设置）；
点主页面上的「开始显示」才重新监听。暂停不存盘，Tab5 重启之后总是从等连接开始。从这个边缘区起手的触摸不发给发送端。

**BYE 之后怎么关连接。** 发 BYE 的一方发完之后**不立刻关连接**：接着把对方还在路上的数据读掉，等对方关了连接再关
（Tab5：从发完 BYE 算起最多等 3 秒；这期间 2 秒没有新数据、对方也没关，就不等了。
这 2 秒要比 TCP 的重传超时长：BYE 或者排在它前面的报文在空中丢了的话，要等重传才到对方，Tab5 上实测是 1.1~1.5 秒）。
收到 BYE 的一方不用回 BYE，不再发数据、马上关连接就行，**不要等对方先关**。
不能发完 BYE 立刻关：这时接收缓冲里还有没读的数据、或者关了之后又有数据到，系统回给对方的是 RST，而有的系统（Windows）
收到 RST 会把接收缓冲里还没读的数据丢掉——对方就读不到这个 BYE，把「对面的人结束的」当成了意外断开。

发 BYE 的一方可以在发完之后先只关发送方向（发送端是这样做的），但对方不能指望这一点：Tab5 不这样做，它到最后才一次关掉
（lwIP 上「先只关发送方向、读到头、再关」这个顺序会重复释放内存，见固件 `wdisp.cpp` 的 `drain_peer`）。

发送端收报文的线程要随到随读，别在里面做耗时的事（注入输入之类交给别的线程）：画面不动的时候发送端没有数据在路上，
Tab5 发了 BYE 之后 2 秒等不到发送端关连接就自己关了；发送端要是这时还没读到 BYE、又发了一帧，换来的是 RST，Windows 上那个还没读的 BYE 就丢了。

**结束之后能不能重连。** 同一时刻只有一条连接，所以发送端什么时候可以自己重连得说清楚：

- 连接是意外断的（没有收到 Tab5 的 BYE，比如 WiFi 抖了一下）：发送端可以自动重连。用自动发现的发送端不照原来的地址连，
  回到广播询问（Tab5 的地址可能已经换了）；手工指定地址的照原地址连。
  一条连接没显示出一帧就断了（认证没过、Tab5 嫌发的东西不合规定、密码框到时间了……），下一次连之前要等：第一次等 1 秒，
  连着这样的话每次加倍，最长 30 秒；显示出一帧就清零。
  重连时偶尔会连接超时（SYN 没有应答）而下一次又好了：发送端这次用的源端口撞上了 Tab5 里还没清掉的上一条连接，
  换一条新连接重试就行，不要当成 Tab5 不在了。
- 收到了 Tab5 的 BYE：是 Tab5 这边的人要结束，发送端**不得照原来的地址自动重连**。
  用自动发现的发送端回到广播询问，等 Tab5 应答了才连——人在 Tab5 上退出之后它不再监听、也不应答询问，要在 Tab5 上点「开始显示」才会再应答。
  手工指定地址的发送端（测试工具）要等用户重新发起。

**出错时 Tab5 的做法。** 协议没有错误报文。发送端发来的东西不合规定（上面任何一条）时，Tab5 直接断开连接、回到等待下一条连接的状态，
原因只记在 Tab5 自己的日志里（开发时对着 `wd_mock_tab5.py` 调，它会把原因打出来）。具体地：

- 握手期间：来的不是这一步该来的那种报文、长度不是表里的定长、`flags` 或 `arg` 不是 0，断开；
- 握手的每一步都限时（见「连上之后走哪条路」的表）：到时发送端的下一个报文没到齐就断开（只连不发的连接不能一直占着唯一的位置）；
- 报文头一到就检查：STRIP 的长度是 0 或超过 `max_strip_bytes`、PRESENT 的长度不是 8、别的报文带了载荷，都不去读载荷，直接断开；
- 报文的认证码对不上，断开；
- 一个报文发到一半（报文头没发完，或者载荷没发完）之后 **5 秒**没有新数据，当作对端失联，断开。第一帧之后，报文与报文之间可以一直不发（画面不变就没有数据）；
- 连接空闲时靠 TCP 保活探测发现对端没了（约 11 秒）。

## 自动发现

发送端不用知道 Tab5 的地址。UDP，端口 `7250`（和 TCP 的端口号一样），询问和应答是同一种 32 字节的包：

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | 标记 | ASCII `T5WD` |
| 4 | 1 | 版本 | 2 |
| 5 | 1 | 类型 | 1 = 询问（电脑发），2 = 应答（Tab5 发） |
| 6 | 2 | 端口 | 应答里是 Tab5 监听的 TCP 端口；询问里填 0 |
| 8 | 16 | 编号 | 应答里是 Tab5 的编号；询问里填 0（Tab5 用不着电脑的编号，电脑也不必把自己固定的编号广播出去） |
| 24 | 8 | 随机数 | 询问里随机取，应答原样带回 |

- 电脑没有连接时每 3 秒往局域网的广播地址发一个询问（每块网卡各发一个），发出后收 300 毫秒的应答，只认随机数是这次询问的那些，
  然后挑一个去连（应答的来源地址 + 包里的端口）：配对过的编号优先；一个配对过的都没有，才连没配对过的（它那边会弹出密码框；
  没设密码、或者已经停止配对时不连）。
  同一个编号从几个地址应答的，一个一个试：上一次在某个地址上一帧都没显示出来就结束了（认证没过（含回了 AUTH_UNKNOWN）、连不上、
  接了就断、发来的东西不合协议……；电脑这边的人要它断的不算），这一轮就把它排到后面，在它上面显示出画面之后才不再排后面。
- **应答里的编号和 HELLO 里的编号必须是同一个**（Tab5 两处报的都是自己的编号）。电脑按应答去连的，连上之后先核对：HELLO 里报的不是
  应答里的那个，就当它不守协议，断开，AUTH、PAIR 都不发。原因：连不连它、它配对过没有是按应答里的编号定的，电脑上「正连着的是哪一台」
  也按它记（人移除一台的配对时，据此断开正连着的那一台）；而握手查配对、存配对用的是 HELLO 里的编号。两个不一样的话，
  一台配对过的设备可以顶着别的编号连上来，之后人移除它的配对，电脑认不出正连着的就是它，那条连接会一直用着已经作废的密钥。
  手填地址去连的没有应答可对，不查这一条。
- Tab5 只在**等连接**的时候应答（已经有连接、暂停着都不应答；开机就在等，和界面在哪一页、息没息屏无关），单播给询问的来源地址和端口；一秒最多应答 10 个。
  连接期间到的询问不留着补答。一条连接从 Tab5 知道它结束的那一刻起就算结束了（Tab5 发 BYE 结束的：发出 BYE 的那一刻；
  别的结束方式：它收到电脑的 BYE、发现连接断了、认定电脑违规的那一刻），没暂停的话，**这之后到的询问都不能丢**：
  电脑收到 BYE 就关连接、马上再问（它自己发 BYE 结束的，等 Tab5 关连接也只等 300 毫秒），这个询问可能在 Tab5 收尾期间就到了，
  被当成「连接期间到的」丢掉的话，电脑要等 3 秒问下一轮才连得上。
  什么时候应答由 Tab5 定，最晚到它关掉这条连接、回到等连接的时候。真机就是到那时才应答（它只在真的能接连接时说自己在）：
  电脑收到 BYE 马上关连接的话只晚几十毫秒；电脑迟迟不关，Tab5 最多等它 3 秒，那时应答已经过了电脑收应答的 300 毫秒，电脑下一轮再问。
- 应答不带认证，也用不着：假的应答把电脑引到别处，握手对不上就断开，画面一个字节都不会发；那边要是说「没配对过」，
  它试密码的次数有上限（见「什么时候可以配对」）。
- 长度不是 32、标记或版本不对、类型不该由自己收的包，直接扔掉。

## 工具（`tools/`，Python，在电脑上跑）

配对和密码（三个工具通用）：
- 配对存在 `--pair-store` 指的 JSON 文件里（权限 0600，不入库）：自己的编号 + 配对过的对方的编号、名字、配对密钥。
  `wd_send_test.py` 和 `wd_bad_sender.py` 默认共用本目录的 `.wdpair_sender.json`，`wd_mock_tab5.py` 默认用 `.wdpair_mock.json`。
- 发送端这边 `--password` 就是「电脑上设的密码」：没和这台 Tab5 配对过、或者它回了 AUTH_UNKNOWN，才用这个密码配对；
  配对过的直接认证，给不给密码都一样。没给密码又要配对，退出码 3。`--forget` 先忘掉所有配对。
- 模拟接收端的 `--password` 是「人在 Tab5 上输的密码」；不给就当作在密码框上点了取消。`--password-delay 秒` 是人输它花的时间
  （默认 8 秒，比握手每一步的 5 秒长，给 0 是秒回；密码框开着的这段时间里发送端只能等，发了东西算违规；到 120 秒 = 人没输完，
  关掉密码框、断开）。它和真机一样最多记 4 台电脑。
- 密码只收 ASCII 的可打印字符、1~64 个，别的直接报错。

各工具：
- `wd_send_test.py <Tab5 地址 | auto>`：测试发送端。握手之后生成测试卡 / 整屏滚动 / 噪点 / 指定图片，按本协议发给 Tab5，
  打印帧率、码率、编码和往返耗时，以及 ACK 里 Tab5 报的接收 / 解码 / 上屏耗时。地址写 `auto` 走自动发现：配对过的优先，
  一个配对过的都没有、又给了 `--password`，才连没配对过的（它从简的地方：只往一个广播地址问、问到就连，不像托盘程序那样每块网卡各问、连不上换下一个）。
  `--name` 是报给 Tab5 的名字（默认机器名）。`--pattern touch` 是触摸回显：把 Tab5 发来的触点画回屏幕（手指周围一个圈、轨迹、
  按下 / 抬起的次数），用手指验证触摸方向、按住不动会不会断、拖动连不连续；在 Tab5 上从左边缘向右滑结束。
  它声明认得 PICTURE_MODE 和 PICTURE（`--caps` 默认 31，五个能力位都置），收到只打印出来：它的质量是 `--quality` 定死的，也没有「画面在动时压小」、不限帧率；
  `--caps 15` 是不说认得 PICTURE_MODE（像加档位之前的发送端），Tab5 这时发折算出来的 PICTURE。
  画面默认走 YUV422（Tab5 说了能走的话）：条带 4:2:2、压到有限范围；`--caps 7` 是不说用它（像加它之前的发送端），走 RGB565、默认 4:2:0；
  `--subsampling 420|444` 也会让它不说用 YUV422。
  `--tone 赫兹` 在画面之外同时发一个正弦波（「声音」；`--tone-db` 是幅度，夜里测给 -50），结果里多一行声音的统计，Tab5 那头的断音次数看调试命令 `wd`。
  `--bye-lag 秒` 收到 Tab5 的 BYE 之后隔这么久才关连接（模拟 BYE 晚到）；`--bye-query` 收到 BYE、关连接之前先单播问一次（自动发现的询问），
  报告 300 毫秒之内有没有应答（配 `--bye-lag 0.05`，测「连接一结束，之后到的询问都不丢」）；`--own-bye-query 秒` 是另一头：
  画面发完、自己发了 BYE 之后隔这么久单播问一次（给 0.015：这时 Tab5 正在收尾）。
  退出码：0 正常结束、1 一帧都没上屏、2 连接中途断了或者 Tab5 发来的东西不合协议、3 认证没过、130 没发完被 Ctrl-C 打断。`--help` 看其余参数。
- `wd_mock_tab5.py`：模拟的 Tab5 接收端。照协议握手、收帧、回 ACK，并逐条检查发送端有没有守上面的规定（握手每一步收什么、时限、
  认证码、内容），违反就说明原因并断开；`--discoverable` 应答自动发现的询问（只在等连接时；连接一结束就算回到等连接、之后到的询问马上应答，
  真机是留到关掉连接之后才应答——发送端收到 BYE 马上关连接时两者没有差别）；
  `--save-dir` 把收到的画面转回横屏存成 PNG；`--inject-input` 在第 3 帧之后（`--inject-at N` 改成第 N 帧）发一组触摸 / 键盘 / HELD / 鼠标报文；
  `--input-mode N` 握手走完之后报触摸方式（0 触摸、1 触摸板，别的数是故意不守协议；不给 = 不报，像老固件；发送端没说认得时不发）；
  `--tpad-gain N` 同样的时候报触摸板加速（N × 0.1 倍，10~50，范围外的数是故意不守协议；不给 = 不报；发送端没说认得时不发）；
  `--picture-mode N` 同样的时候报画质的档位（0~3，别的数是故意不守协议；`--frame-us 微秒` 是一起报的屏幕帧周期，默认 15270，5000~50000 之外是故意不守协议）：
  发送端认得 PICTURE_MODE 就发它，只认得 PICTURE 的发折算出来的 PICTURE，都不认得的不发；
  `--picture 质量,预算KB` 是像加档位之前的固件那样直接报一组质量和预算（例 `85,60`；质量在 1~100 之外是故意不守协议；不给 = 不报；发送端没说认得 PICTURE 时不发）；
  `--no-audio` 是 HELLO 里不说能收声音（像加声音之前的固件，发送端这时发 AUDIO 算违规）；
  `--no-yuv` 是 HELLO 里不说能走 YUV422（像加它之前的固件，发送端这时在 AUTH 里说用它算违规）；发送端说了用 YUV422 的连接上，
  它只收 4:2:2 的条带，存下来 / 拿来比的画面是把有限范围展开之后的（真机上是 DSI 桥展开的）；
  `--bye-after N` / `--drop-after N` 在第 N 帧之后发 BYE 结束 / 直接断开，用来测发送端「收到 BYE 不重连、意外断开才重连」；
  `--late-ack N:秒` 让第 N 帧的 ACK 晚到（模拟它在空中丢了），用来测发送端的流量控制。写发送端（包括 C# 版）时先对着它调，不用占着真机。它量不出真机的解码和上屏耗时。
- `wd_bad_sender.py <Tab5 地址>`：不守协议的发送端。开头先守规矩地握手一次（没配对过的在这里配对），然后一条一条地故意违规，
  每条用一条新连接，检查接收端是不是在时限内断开、之后还能不能正常用。分三组：握手里的违规（该来的报文不来、长度 / 字段不对、
  公钥全 0、点不在曲线上、收到 AUTH_UNKNOWN 之后不照规矩走、密码框开着的时候又发报文……）、认证码对不上的（改一个比特、重放、
  换先后、握手之后发明文）、内容不合规定的（含二十几种结构不对的 JPEG、报文发到一半就不发、连上之后不发完第一帧）。
  对着真机它看不到断开的原因，所以判得严：该先回 AUTH_UNKNOWN、AUTH_OK + READY 的几项要先收到它们；守规矩的那一段就被断开的算没测到；
  该等满 5 秒才断的几项，不到 4 秒就断了也判不符。「密码框开着又发 PAIR」那一项会让真机的密码框弹一下（连接一断就关，不用人输）。
  `--only 字样` 只跑名字里带这个字样的用例（比如 `--only AUDIO`）；`--fuzz N` 再加 N 轮随机改文件头的条带，`--fuzz-body N` 再加 N 轮压缩数据被改坏的整屏画面（坏数据会进解码器）。
  改了 Tab5 的接收端之后对着真机跑一遍，也可以对着 `wd_mock_tab5.py` 跑。
- `wd_selftest.py`：上面几个脚本的自测（本机回环，不需要 Tab5），含密码学（RFC 9382 附录 B 的向量、`../testvectors/v2.json`）、
  握手的各条路、违规发送端的每一项和它自己的判定、自动发现。`--write-vectors` 重新生成 `../testvectors/v2.json`。
- `wd_discover.py`：广播自动发现的询问，打印哪些 Tab5 应答了、各用了多久，并数出有几次落在发送端收应答的 300 毫秒之内
  （Tab5 等连接时 WiFi 在省电，广播要等信标才送到它；实测应答 20~95 毫秒）。
- `wdproto.py`：报文头、各载荷的排布、握手（两侧）、配对存储、自动发现、几何换算。协议改了先改本文件，再改它。
- `wdcrypto.py`：SPAKE2（P-256）、密码 → `w`、配对密钥、密钥标识、X25519、会话密钥、逐报文加解密。
  P-256 的点运算用的是 Python 大整数，**不防旁路，只给测试工具用**；固件和 C# 发送端各有自己的实现。
- `../testvectors/v2.json`：测试向量——RFC 9382 附录 B 的四组，加上本协议的密码 → `w`、配对、会话密钥、报文加密各一组
  （配对的两种都带着中间值 K、TT、Ka、KcA、KcB：对不上时看得出错在哪一步），和一组该拒的输入（不合格的点、让 K 成为无穷远点的点、
  X25519 的低阶公钥）。固件、C# 发送端、Python 工具对同一份。

## 还没做的

- 声音的音画对齐（带时间戳）、压缩（Opus）：现在是不压缩、不对齐、按到的先后放（见「声音」），`0x41`~`0x4F` 留给它们。
- MOUSE（`0x22`）留着没用：触摸板方式是电脑把触点换成鼠标动作（见「触摸方式」），Tab5 自己不发鼠标报文。
- **多台电脑时在 Tab5 上选一台**（理论上不会有两台电脑同时开着发送端，记下来以后做）：现在 Tab5 同一时刻只接一台，
  谁的询问先到谁连上，Tab5 上选不了；A 断开后 B 接手，A 回来抢不回去；局域网里有设了密码、没配对过的电脑在跑发送端时，Tab5 等连接期间会被它弹密码框。
  想法：在「已配对的电脑」里加「只接这一台 / 自动」。现在的询问包不带电脑编号，Tab5 分不出是谁在问，所以要动协议——询问里带上编号，
  或者握手时加一个「现在不接你」的答复（发送端收到后安静地等，不按「没显示出画面就结束」加倍等待），用能力位协商。
  一台电脑对多台 Tab5 现在已经能控制（在不想用的那台上做退出手势暂停，它就不再应答）；两台 Tab5 同时显示是另一个功能（发送端要开多条会话），没有计划。
