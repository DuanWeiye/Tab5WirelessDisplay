# 无线显示：认证和加密（设计取舍）

> 要求：托盘程序里设一个密码（长度不限）；Tab5 第一次连接时在屏幕上用软键盘输入，对上之后不再问；加密要做，但不能拖慢传输。
> 定下来的做法：SPAKE2 配对（Windows 端为此引 BouncyCastle）、帧率验收线「开加密后掉不超过 3%」、局域网广播自动发现。
> **本文件讲取舍；报文和算法的细节以 `PROTOCOL.md`（v2）为准。** 和最初的草案不一样的地方（下面的正文已经照改）：
> - **配对是全自动的，电脑上设了密码就随时可以配对**，不设「人在电脑上开 5 分钟配对窗口」。
>   冒充 Tab5 的程序能让电脑替它验证密码猜测，这一点用次数上限挡：
>   密码不对累计满 10 次（存盘，重启不清零）电脑就停止配对，要人在托盘里点一下恢复；配对成功或改密码清零。正常使用碰不到。
>   （先做过「越试越慢、过一阵自己恢复」的版本：短密码拖得够久还是会被试出来，配上就能往电脑注入键盘，所以改成有上限的。）
> - AUTH 里带配对密钥的标识：两边存的不是同一把时 Tab5 回「不认识」，可以重新配对；草案里这种情况两边会永远对不上。
> - 新配的密钥等同一条连接上的握手走完才存；配对成功后在同一条连接上接着握手，不用断开重连。
> - 「各发一个校验值」做成了各发一个加密的空报文 READY（认证码对上就证明有密钥），少一种单独的校验算法。
> - 设计审查之后补的细则：配对成败怎么算（存下来才算成功、每核对出一次密码不对记一次）、
>   改密码 / 移除配对时断开正连着的、询问包里不带电脑的编号。

## 要挡住什么

家里局域网里的另一台设备（或者能看到这段流量的人）：旁听画面和键盘输入；冒充 Tab5 骗电脑把屏幕发给它；冒充电脑连上 Tab5 收键盘输入、往屏幕上放东西；
中途改报文。密码可能很短，所以**抓到握手报文的人不能拿它在自己电脑上慢慢猜密码**。
不挡的：拿到 Tab5 本机的人（闪存没加密，存的密钥读得出来）、电脑本身被攻破、从报文的长度和时刻推测内容、
局域网里的人捣乱让你用不了（抢着应答询问、占着唯一的连接、反复弹密码框——画面和按键他拿不到）。

## 分两步：配对一次，之后每次连接用配对留下的密钥

**配对（只在第一次，或者配对被清掉之后）**
- 用 SPAKE2（RFC 9382，P-256）：一种「拿密码换密钥」的标准做法。两边各拿密码算一步、交换一个点，密码一样才能算出同一个密钥。
  报文里没有能用来验证「猜的密码对不对」的东西：旁听的人猜不了；冒充一方的人每连一次只能试一个密码。
- 流程：电脑连上（没有这台 Tab5 的配对）→ 电脑发它那一步 → Tab5 弹出密码框（屏幕软键盘）→
  输完 Tab5 发它那一步和校验 → 电脑核对、回校验 → 两边各存一把随机的 32 字节**配对密钥**。Tab5 存 NVS（最多记 4 台电脑），电脑存在当前用户的配置里（DPAPI 加密）。
- 输错：Tab5 上密码框标红、清空重输。电脑那边累计错满 10 次就断开、停止配对，托盘图标变成出错的样子，点一下恢复。
- 为什么不用更简单的「先交换密钥、再在加密通道里对密码」：能在配对那一刻插在中间的人，可以把校验值带回去离线猜出短密码。SPAKE2 没有这个洞，
  而且 RFC 里有标准测试向量，两边的实现各自对着向量测。代价是两边都要做椭圆曲线上的点运算：Tab5 用 mbedtls 现成的；
  Windows 的 .NET 不提供，要引 BouncyCastle 这个库（纯托管代码，约 3 MB）。

**每次连接（配对过之后）**
- Tab5 的 HELLO 带设备编号 → 电脑带自己的编号、配对密钥的标识、一次性的 X25519 公钥 → Tab5 回它的公钥 → 两边用「配对密钥 + 这次交换出的密钥」
  导出两个方向各一把会话密钥，并各发一个加密的空报文证明自己有配对密钥。对不上就断开，什么数据都不发。
- 带一次性密钥交换是为了：以后配对密钥万一泄露，以前录下来的流量也解不开。Tab5 上实测一次连接多 0.12 秒。
- 任何一边不认识对方、或者两边存的不是同一把密钥（Tab5 被重置、电脑清了配对、上次配对的最后一步断了）→ 回到配对（Tab5 上再输一次密码）。

## 报文加密

- 握手之后**所有**报文都加密：ChaCha20-Poly1305，每个报文一个 16 字节的认证码。8 字节的报文头不加密但算进认证码（改了头也过不了）。
  每个方向一个从 0 开始的 64 位计数器当一次性数，所以重放、丢、换顺序都会被发现；任何一个报文认证不过就断开。
- 选它是量出来的（`firmware/tools/cryptobench/`，Tab5 上硬件加密不可靠、全用软件）：ChaCha20-Poly1305 6.8 MB/s，AES-GCM 只有 0.8 MB/s。
  Windows 上这个算法系统自带，一秒几百 MB，不用管。

## 会不会拖慢

- 现在一帧 35.7 毫秒（28 帧/秒）：Tab5 收数据约 10 毫秒（大部分时间在等网络）、解码 6、上屏 9，其余在电脑那边。一帧平均 42 KB，解密要 6 毫秒。
- 做法：**边收边解密**——数据到一块解一块，写进原来的缓冲，整个报文的认证码对上了才交给 JPEG 解码器。解密用的是原本在等网络的时间。
- 预计：28 → 27 帧/秒上下；整屏噪点那种极端画面（一帧 430 KB，现在 7.5 帧/秒）会掉得多一些。
- **验收**：真机上同一个固件开 / 关加密各跑一遍测试卡、整屏滚动、真实投屏，帧率差 3% 以内算过。差得多就再做一步：把解密挪到另一个核上的任务里，
  和解码并行。（手工优化 ChaCha20 试过，只快 33%，这颗 CPU 没有循环移位指令，不走这条路。）

## 界面（按精简风格）

- Tab5「无线显示」页：等连接时不变。配对时弹密码框，标题带电脑的名字（已经配对过的电脑又来配对，写「重新配对」），输错只把框标红。设置页加一行「已配对的电脑」，点进去是名字列表，可以移除（这一行后来挪到了「无线显示」页上；固件只留无线显示之后，那一页就是主页面，密码框挂在顶层、界面在哪一页都弹）。
- Windows 托盘菜单：「配对密码」（已设置 / 未设置；密码错太多次停止配对时这一行用错误色写「已停用」，点一下恢复）、「已配对的设备」（列表，可以移除）。
  **改密码 = 清掉所有配对**，各台 Tab5 下次配对时重新输。

## 托盘程序怎么找到 Tab5（和「自动连接」有关）

- 不用人填地址：托盘程序每 3 秒在局域网里广播一个很小的询问包，Tab5 只在等连接的时候（最初是「无线显示」页开着时；现在开机就在等，暂停着才不应答）回一句「我在这，端口 7250，设备编号…」，
  托盘程序收到就连。回的包是对电脑发出去的包的应答，按 Windows 防火墙的默认设置会放行、不用弹框让人点允许（实测过）。
- 骗不了人：假的应答把电脑引过去，握手对不上就断开，屏幕内容一个字节都不会发；没配对过的设备要人在它上面输对密码才连得上，试密码的次数有上限。
- 协议里「收到 Tab5 的 BYE 之后发送端不得自动重连」这条不变：人在 Tab5 上退出之后 Tab5 不再监听、也不再应答询问，要在 Tab5 上重新打开页面（现在是点主页面上的「开始显示」）才会再连上。

## 测试工具

- Python 的发送端、模拟接收端、违规发送端、真机回归都改成走同一套握手和加密（密钥用一次配对存下来的），**固件里不留明文模式**——
  不然回归测的就不是实际用的那条路。帧率的回归数字从此是带加密的数字。
- `wdsend --allow-plaintext` 和明文那条路随之删掉。
